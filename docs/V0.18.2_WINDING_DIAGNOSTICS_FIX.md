# V0.18.2 Motor-CAD 绕组可解性与日志根因修复

## 1. 本次实际失败的根因

本次分析使用用户上传的诊断包和完整运行数据。最新失败任务为：

- Task：`TASK-5359E95EE8`
- Project：`aaa / PRJ-4BAEF748D9`
- Design Revision：`REV-45A71BE125`
- Template：`i5_Industrial_SPM_Servo_Tooth_Wound`
- Analysis：`emag`
- Solver：Motor-CAD

Design Rev.1 数据库快照的关键绕组参数为：

- `slot_count = 12`
- `parallel_paths = 1`
- 模板 MTT：`MagPhases = 3`
- 模板 MTT：`Slot_Number = 12`

任务提交时出现一项显式覆盖：

- `slot_count: 12 -> 16`
- `explicit_parameter_ids = ["slot_count"]`

因此当前绕组关系变为：

`Slot_Number / Phases / ParallelPaths = 16 / 3 / 1 = 5.33333`

Motor-CAD 原生 `MessageLogs` 在 FEA 启动前已明确报告：

- `Winding is not feasible.`
- `Slot_Number/Phases/Parallel Paths not integer value = 5.33333`
- `Slot fill = 1.094 should not be > 1`

随后执行电磁求解时继续报告：

- `Fundamental winding factor = 0.`
- `Check winding definition is correct.`
- `Unable to solve Fea problem`

所以当前失败属于确定性的绕组拓扑/绕组定义不可行，与 Motor-CAD 安装、RPC 链路或许可证获取失败无关。日志显示 EMag 许可证已获取，Motor-CAD worker 已正常启动。

## 2. 为什么旧版会让用户误以为模型“应该能算”

旧版的运行时 `model_validation.json` 同时记录：

- `geometry_api_succeeded = true`
- `winding_refresh_attempted = true`
- `winding_refresh_succeeded = true`

这里第二个 `true` 的语义有缺陷：代码只检查 `create_winding_pattern()` 是否抛出 Python 异常。Motor-CAD 在 API 调用返回后已经通过 MessageLog 报告绕组不可行，Studio 没有继续读取并解释这些原生消息。

同时 `check_if_geometry_is_valid(0)` 返回成功。几何有效与绕组可解是两个独立门禁，因此“Geometry check successful”不能证明电磁模型可求解。

## 3. 现有日志系统的准确性评估

原始证据层基本完整，诊断解释层存在明显缺口。

### 已经能够记录的内容

中央结构化日志已经捕获 `SOLVER_CHILD_EXCEPTION`，其中包含 Motor-CAD 的完整 winding error。Case `error.log` 也能保存最终异常。因此在人工逐条阅读原始日志时，可以找出根因。

### 旧版不足

1. 问题中心优先展示 `TASK_FINISHED: FAILED`、`CASE_FAILED` 等后果事件，真实的 `SOLVER_CHILD_EXCEPTION / winding` 根因排名靠后。
2. 没有 `WINDING` 类别及槽/相/并联支路关系识别，推荐项只能提示继续查看时间线。
3. `winding_refresh_succeeded = true` 具有误导性，没有区分“API 调用成功”和“绕组实际可行”。
4. 在线诊断 ZIP 主要收集日志类 artifact，没有自动携带 `model_validation.json`、`runtime_defaults.json` 和嵌套 Motor-CAD `MessageLogs`；本次需要第二个完整数据包才能看到 FEA 前的原生证据。
5. `/api/validate` 前端请求遗漏 Project / Design Revision / explicit parameter intent，导致提交前检查无法完整体现设计血缘和参数覆盖。
6. Data Factory 在失败任务结束前记录 `INGEST_READY / status=READY`，其含义是数据摄取完成，但界面/日志语义容易被理解为任务或结果 Ready。

## 4. V0.18.2 修复

### 4.1 提交前绕组可解性门禁

增加 `winding_guard.py`。对已经有实机证据的模板使用数据驱动约束。i5 模板在 `template_profiles.yaml` 中明确配置：

- `phase_count: 3`
- `require_integer_slots_per_phase_path: true`

当 `slot_count=16, parallel_paths=1` 时，提交前直接生成：

- Code：`WINDING_SLOT_PHASE_PATH_NONINTEGER`
- Severity：`BLOCKING`
- 原因：`16 / 3 / 1 = 5.33333`
- 模板基线：12 slots
- 邻近整数倍候选：15、18

这样不会再为确定性不可解设计启动 Motor-CAD worker。

约束只对已经显式验证的模板启用硬阻断，避免把所有 PM 电机粗略套用同一个整数规则，给合法的其他绕组拓扑造成误阻断。

### 4.2 Design Revision 差异追踪

`/api/validate` 会读取不可变 Design Revision 参数快照，并对任务参数计算 delta。本次会显示：

`slot_count 12 -> 16`

Code：`DESIGN_REVISION_TASK_OVERRIDE`。

这样用户可以区分“当前设计版本是什么”和“本次 Task 临时改了什么”。

### 4.3 前端预检查与正式提交使用同一上下文

`validateCurrent()` 现在同步提交：

- `project_id`
- `design_revision_id`
- `scenario_revision_id`
- `explicit_parameter_ids`
- 全部求解/材料/场景参数

避免预检查与最终 `/api/tasks` 的数据血缘不一致。

### 4.4 运行时 Motor-CAD 原生绕组诊断

`_validate_model()` 现在记录：

- `winding_precheck`
- `winding_refresh_attempted`
- `winding_refresh_api_succeeded`
- `winding_refresh_succeeded`
- `winding_validation`
- `winding_native_message_count`

Studio 会同时读取 `mc.get_messages(0)` 与当前 Case 目录的原生 `MessageLogs`。检测到下列消息时生成结构化诊断：

- winding infeasible
- Slot/Phase/ParallelPaths 非整数
- slot fill > 1
- fundamental winding factor = 0
- FEA 因绕组问题中止

并抛出 `WindingValidationError`。Case stage 会标记为 `WINDING_INVALID`。

### 4.5 问题中心改为根因优先

新的诊断聚类加入：

- `WINDING`
- `GEOMETRY`
- `IPC`
- `TIMEOUT`
- `LICENSE`
- `PARAMETER_MAPPING`
- `DATA_FACTORY`
- `STORAGE`

每个问题增加：

- `root_cause`
- `consequence`
- `problem_score`

`TASK_FINISHED: FAILED` 会降权；包含明确 Motor-CAD winding error 的 `SOLVER_CHILD_EXCEPTION` 会成为首要根因。Task 详情页直接显示最高优先级根因。

### 4.6 诊断包自包含

Task 诊断 ZIP 现在自动加入：

- `task_state.json`
- `root_cause.json`
- `case_diagnostics/index.json`
- `error.log`
- `solver_runtime.jsonl`
- `model_validation.json`
- `model_load.json`
- `runtime_defaults.json`
- `parameter_audit.json`
- `material_audit.json`
- `output_audit.json`
- `checkpoint_manifest.json`
- `case_manifest.json`
- Motor-CAD `MessageLogs/messageLog_*.txt`

因此后续只导出一个诊断包即可完成同等级别的离线根因分析。

### 4.7 Data Factory 事件语义

`INGEST_READY` 改为 `INGEST_COMPLETE`，同时明确记录 `semantics=data_ingestion_only`。Task Manager 的摄取事件也会附带最终任务状态，并说明数据归档完成不代表求解成功。

## 5. 当前数据的直接恢复建议

当前 `aaa` 项目的 `REV-45A71BE125` 基线已经是 12 槽。建议先保持以下绕组关键参数：

- `slot_count = 12`
- `parallel_paths = 1`
- `phase_count = 3`（模板定义）

然后重新运行“模型可解性检查”。不要直接重试现有 `TASK-5359E95EE8`，因为该 Task 的不可变请求仍保存 `slot_count=16`。

当前历史数据中，同一 i5 模板、12 槽的 `TASK-CB30898B81` 已两次写出 `SOLVER_RUN_SUCCESS`。它最终被旧版 Windows IPC `WinError 109` 收尾竞态误记为失败，这一问题已经在 V0.18.0 修复。该记录能证明 12 槽基线至少已经通过真实 Motor-CAD 求解路径。
