# V0.18.1 模板 → Design 工作流修复

## 1. 日志证据

用户诊断包在 2026-08-13 14:32（UTC+8）记录 `POST /api/projects -> 201`，随后 14:33 记录 `POST /api/templates/e14_eMobility_AFM/geometry-precheck -> 200`。之后没有 `POST /api/designs` 或 `POST /api/designs/{id}/revisions`。这说明后端项目与模板接口均可用，流程在浏览器端“模板选择 → 创建确认”之间中断。

## 2. 根因

V0.18.0 的模板点击处理同时执行：

1. `showTab('workspace')`，内部异步调用 `loadWorkspace()`；
2. `await openWorkspaceProject(activeProjectId)`；
3. `createWorkspaceDesignFromTemplate()` 在右侧 inspector 渲染创建表单。

第 1 条和第 2 条形成并发工作区刷新。若 `loadWorkspace()` 较晚返回，它会再次渲染项目首页并覆盖第 3 条刚生成的创建表单。由于确认按钮随 DOM 被替换，浏览器不会发起创建 Design 的 API 请求。

## 3. 修复

- 模板选择只设置 `workspaceCreateTemplateId` 并进入工作区，不再并发显式加载同一个项目。
- `openWorkspaceProject()` 每次完成刷新后检查待处理模板；待处理动作存在时重新渲染创建确认页。
- 创建表单移动到工作区主画布，并在右侧属性面板同步显示模板/目标项目，避免关键操作藏在窄面板。
- 取消、成功创建或切换项目时清除待处理状态；提交期间加入 busy 锁，阻止重复创建。
- 新增 `POST /api/projects/{project_id}/designs/from-template`，服务端校验模板并一次创建 Design + Rev.1。
- Design 与 Rev.1 使用同一 SQLite 事务；任一步失败会整体回滚。
- Rev.1 参数快照直接来自服务端 TemplateService，前端不再自行发送模板 defaults。

## 4. 回归测试

新增 `tests/test_v0181_template_design_flow.py`，覆盖：

- 模板原子应用创建 Design + Rev.1；
- 不存在模板不会产生半成品 Design；
- 强制 Rev.1 插入失败时 Design 同步回滚；
- 前端待处理模板状态会在工作区刷新后恢复；
- Client Contract 暴露 atomic template design create 能力。

完整测试：`106 passed`。同时通过 `python -m compileall` 与 `node --check`。
