# MotorCAD Studio V0.67.0：Analysis / Compute Workflow Closure

## 1. 本轮目标与路线位置

V0.67 的目标是补回前期为了治理 Design Workbench 架构而延期的“分析与计算闭环”。前面的路线可以概括为：

- V0.62：前端状态、路由和信息架构收敛；
- V0.63：Design Workbench、Draft 编辑与连续设计流程；
- V0.64：Design Renderer 和材料体系的模块化；
- V0.65：Draft 并发一致性、编辑器生命周期和验证边界；
- V0.66：几何/绕组/材料/设计验证工程可视化补齐，并恢复原路线；
- **V0.67：把 Analysis Definition、工况、物理输入、Solver、Precheck、Task Submission、Monitor 重新压缩成一条可执行的工程链。**

因此 V0.67 不再扩展 Design 页面，也没有再建立一套新的 Task 配置概念。核心工作是确定“计算到底由哪一份设计、哪一份分析输入、哪一套求解配置驱动”，并让普通工程师沿一条路径完成检查、提交和监控。

本轮完成后的正常路径为：

```text
Project
  └─ Motor Design
       └─ Design Revision（不可变）
            └─ Analysis Definition
                 └─ Analysis Revision（不可变）
                      ├─ 工况 / load cases
                      ├─ 物理输入
                      ├─ Solver settings
                      └─ Requested outputs
                           ↓
                      Execution Plan
                           ↓
                  Studio Precheck
                           ↓
               Motor-CAD Native Check
                           ↓
             Revision-bound Evidence
                           ↓
                Immutable Run Config
                           ↓
                       Task
                      /    \
                   Case   Case ...
                      \    /
                   Live Monitor
                         ↓
                 Result Validation
                         ↓
                      Results
```

这里有三个明确的数据边界：

1. **Design Revision** 冻结长期设计定义；
2. **Analysis Revision** 冻结本次分析的工况、物理输入、求解设置和结果请求；
3. **Run Configuration** 冻结真正提交给计算任务的最终配置及来源。

这三个边界使“设计已改”“分析设置已改”“真正算的是哪一版”可以被独立追溯。

## 2. V0.66 之前分析/计算流程的主要断裂点

V0.60 已经具备 Analysis Definition、物理输入编辑器、计算前检查和多工况物化，V0.21 以来也已经有 Run Configuration、Scenario、Solver Profile、Output Profile 等底层资产。但是经过多轮演进后，普通界面仍存在以下问题。

### 2.1 Analysis Workbench 与 generic `newTask` 并存

工程师从分析页面进入计算时，仍可能被带到通用 Task Builder。此处展示的概念比正常工作流需要的多，也造成“分析设置完成后还要再配置一遍 Task”的感受。

V0.67 将 `newTask` 降级为高级兼容入口。普通流程不再通过它完成计算提交。

### 2.2 Precheck 存在多个所有者

旧 Workbench 自己可以执行计算检查，之后计算入口还会重复检查。这样产生两个问题：

- 工程师不知道哪个检查才是最终提交门禁；
- 原生 Motor-CAD 模型检查可能重复执行，增加等待时间并扩大 RPC 竞态面。

V0.67 将计算 Precheck 的唯一普通流程所有者迁移到 `analysis/execution.js`。

### 2.3 浏览器显示的 Analysis Revision 与服务端实际提交之间缺少强一致性边界

用户可能在窗口 A 打开 Rev.A2，同时窗口 B 已经创建 Rev.A3。如果窗口 A 直接点击计算，服务端重新读取“最新版本”时就可能把 A3 提交出去，而 A 窗口仍以为自己提交的是 A2。

V0.67 对 Precheck 和 Execute 都增加 Design Revision / Analysis Revision 身份验证。发现浏览器计划过期后，返回结构化 HTTP 409，并强制重新加载执行计划和重新检查。

### 2.4 Precheck 结果没有形成可复用的版本化证据

如果 Precheck 与 Execute 之间只是一个布尔值，服务端无法回答“这个 Motor-CAD 检查到底检查的是哪一版”。V0.67 将通过检查的证据绑定到明确的 Design Revision + Analysis Revision，并设置短期 TTL。

### 2.5 Monitor 缺少工程对象血缘

Task Monitor 可以看到任务和 Case，但工程师还需要知道该计算来自哪个 Analysis Revision、哪个 Design Revision 和哪个 Run Configuration。V0.67 增加 workflow-status 汇总并放入 Monitor 顶部。

## 3. 新的六阶段 Analysis / Compute Workbench

V0.67 在稳定目录中建立：

```text
static/analysis/
  workbench.js     # 分析案例浏览与入口
  execution.js     # 六阶段执行工作流唯一所有者
  monitor.js       # Task Monitor 的工程血缘增强
```

历史 `static/v060.js` 已从活动树物理删除。

正常分析/计算流程固定为六步。

### 3.1 Step 1：工况

展示当前 Analysis Revision 的实际 load cases，而不是额外创建一份临时计算工况。

页面回答：

- 当前有几个工况；
- 每个工况的转速、电流、电压、相位角等是什么；
- 是单点、批量还是配方定义的工作点；
- 实际会生成多少 Case。

工况来源仍由当前分析配方和 Analysis Revision 管理，执行页面只做确认和计算物化。

### 3.2 Step 2：物理输入

系统根据分析配方声明的 required input domains 汇总输入准备度，例如：

- 冷却；
- 损耗；
- 材料；
- 接触界面；
- 辐射；
- 对流；
- 端部空间；
- 流动回路。

缺少必需物理输入时，页面直接显示缺失项并禁止进入可提交状态。输入修改仍复用现有 Input Data 编辑器，完成后回到同一 Analysis/Compute 深链接，而不是进入另一套流程。

### 3.3 Step 3：求解设置

展示当前 Analysis Revision 最终生效的：

- 求解器配置；
- 质量/精度档位；
- 配方 native automation 设置；
- 请求输出；
- Case 数量；
- Task validation 状态。

该页面以“有效计算合同”为中心，不向普通工程师暴露 Worker lease、内部 RPC payload 等平台实现细节。

### 3.4 Step 4：Precheck

V0.67 的 Precheck 是正式计算门禁，包含两个层级：

1. **Studio deterministic check**：几何、绕组、物理输入、工况和求解合同的确定性检查；
2. **Motor-CAD native model check**：目标环境可用时，对实际 Motor-CAD 模型执行原生检查。

Precheck 请求携带浏览器正在查看的：

```text
expected_analysis_revision_id
expected_design_revision_id
```

服务端在原生检查之前和之后都验证 Revision 身份。因此即使原生检查持续较长时间，另一个窗口在中间创建了新 Analysis Revision，也不会把旧检查结果错误登记到新 Revision。

### 3.5 Step 5：提交计算

只有通过当前 Revision Pair 的 Precheck 后才能进入可提交状态。

正常提交调用：

```text
POST /api/analysis-definitions/{analysis_id}/execute
```

请求中包含：

- expected Analysis Revision ID；
- expected Design Revision ID；
- Precheck evidence ID；
- submission key；
- quality profile；
- cache reuse 策略；
- 是否允许缺少有效 evidence 时重新执行 native precheck。

服务端不会直接信任浏览器生成的 Task payload，而会重新从当前权威 Analysis/Design Revision 构建 execution request、执行 Task validation、创建 immutable Run Configuration，再创建 Task。

### 3.6 Step 6：运行监控

提交成功后进入 Monitor，并显示：

- Analysis Definition；
- Analysis Revision；
- Motor Design；
- Design Revision；
- Run Configuration；
- Task stage / progress；
- Case 总数；
- 已完成 Case；
- 失败 Case；
- 可用结果 Case；
- 结果是否可以进入。

因此 Monitor 从“任务运行窗口”升级为“本次工程计算的血缘与执行状态窗口”。

## 4. Execution Plan：将分析设置收敛为一个权威计算合同

新增：

```text
GET /api/analysis-definitions/{analysis_id}/execution-plan
```

该接口从一个 Analysis Definition 生成当前可执行计划，并返回：

- Analysis Definition / Analysis Revision；
- Design / Design Revision；
- operating points / load cases；
- input domains 和缺失项；
- solver settings；
- requested outputs；
- Studio precheck；
- Task validation；
- static runtime readiness；
- 完整准备后的 Task request；
- recent Tasks；
- `can_submit`。

这一接口的意义是把过去分散在 Analysis、Input Data、Task Builder、Precheck 页面中的信息压缩成一个服务器权威视图。

前端不会自行拼接一份“看起来像最终任务”的数据结构。最终计算合同始终由服务端基于持久化 Revision 重新生成。

## 5. Revision stale guard：关闭多窗口静默错算风险

新增统一校验器：

```text
_assert_analysis_execution_identity(...)
```

当浏览器携带的 Revision 与当前 Analysis Definition / Design 绑定不一致时，返回：

```json
{
  "code": "ANALYSIS_EXECUTION_STALE",
  "message": "分析设置或设计版本已在其他窗口更新，请刷新执行计划后重新检查。"
}
```

HTTP 状态码为 409。

前端接收到该错误后执行：

1. 清除旧 `fullCheck`；
2. 清除旧 precheck evidence；
3. 清除当前 submission state；
4. 重新读取 execution plan；
5. 显示新 Analysis Revision / Design Revision；
6. 保持“提交计算”锁定；
7. 要求对新 Revision Pair 重新执行 Precheck。

该机制避免两类高风险情况：

- 浏览器窗口停留在旧 Analysis Revision，却静默提交最新 Analysis Revision；
- Design Revision 已切换，旧 Precheck 仍被误认为对新设计有效。

测试同时验证：发生 409 时 **不会创建 Task**。

## 6. Revision-bound Precheck Evidence

V0.67 新增短期 Precheck evidence store。默认 TTL 为 900 s，并限制内存中证据数量。

证据保存：

- evidence ID；
- Analysis ID；
- Analysis Revision ID；
- Design Revision ID；
- Studio Precheck 状态；
- native model check 结果；
- 生成时间/过期时间。

一个关键实现点是：证据绑定的是**执行检查时捕获的 Revision Pair**，而不是检查结束后再次查询“当前最新 Revision”。

因此：

```text
A2 + D4 通过 Precheck
        ↓
生成 evidence(E1, A2, D4)
        ↓
其他窗口创建 A3
        ↓
E1 不能用于 A3 + D4
```

如果 Execute 收到仍有效且匹配的 evidence，就直接复用，避免同一次操作中重复启动 Motor-CAD 原生检查；如果 evidence 缺失/过期且允许 native precheck，则执行端重新检查后再提交。

## 7. Immutable Run Configuration 与幂等提交

V0.67 没有绕开原有 Task 核心模型，而是把 Analysis Workbench 正确接回已经成熟的 Run Configuration / Task 层。

`execute` 最终仍调用现有 `create_task()`，它负责：

1. `tasks.prepare_request(payload)`；
2. submission-key 幂等检查；
3. Motor-CAD runtime readiness gate；
4. Task request validation；
5. 创建 immutable Run Configuration；
6. 创建 Task / Case。

因此同一提交请求发生浏览器重试、网络响应丢失或用户快速重复点击时，`submission_key` 用于阻止重复任务。

Run Configuration 是真正的计算复现边界，记录本次计算冻结的设计、工况、求解器和输出配置。历史 Task 不会随着后续 Design Revision / Analysis Revision 修改而变化。

## 8. 工况到 Motor-CAD 求解器的实际数据链

TaskManager 在每个 Case 开始前会把 scenario/load-case 变量物化为 canonical parameter overrides，再交给 solver adapter。

因此工况链路为：

```text
Analysis Revision load case
    ↓
Scenario parameter overrides
    ↓
Canonical parameter registry
    ↓
Motor-CAD automation variable mappings
    ↓
Native calculation API
```

当前 Motor-CAD solver adapter 已覆盖现有配方需要的主要路径，包括：

- electromagnetic calculation；
- steady-state thermal analysis；
- transient thermal analysis；
- magnetic-thermal coupled calculation；
- weight / mechanical paths；
- saturation map；
- torque envelope；
- Motor-CAD Lab model build / magnetic Lab / operating point Lab。

17 类 Analysis Recipe 继续负责描述使用哪类求解、需要什么物理输入、默认工况、native automation 字段和结果请求。V0.67 没有把这些规则重新硬编码到 UI。

## 9. 路由、刷新与异步生命周期

执行工作流支持精确深链接：

```text
/app/projects/{project}/simulation/analyses/{analysis}/execute/cases
/app/projects/{project}/simulation/analyses/{analysis}/execute/inputs
/app/projects/{project}/simulation/analyses/{analysis}/execute/solver
/app/projects/{project}/simulation/analyses/{analysis}/execute/precheck
/app/projects/{project}/simulation/analyses/{analysis}/execute/submit
/app/projects/{project}/simulation/analyses/{analysis}/execute/monitor
```

这意味着：

- F5 可以恢复到具体执行步骤；
- 浏览器 back/forward 可以恢复步骤；
- 从 Input Data 返回时可以明确回到 Precheck；
- 从 Monitor 返回时可以回到对应 Analysis 的 monitor 阶段；
- URL 自身能够表达当前工程上下文。

对耗时 Precheck / Submit 请求增加 route/session token。用户关闭执行器或切换路由后，晚返回的请求结果会被丢弃，不能重新打开弹层、覆盖新 Revision 或跳转到错误 Monitor。

Playwright lifecycle contract 已专门覆盖这一行为。

## 10. Legacy `newTask` 的处理

V0.67 没有立即删除 generic Task Builder，因为高级调试、兼容历史路径和底层资产测试仍可能使用它。

当前定位明确为：

- 普通工程师：`分析与计算`；
- 高级/兼容：`高级任务配置`。

普通项目流、Analysis Workbench、Input Data 返回、Precheck 入口不再跳转 `newTask`。

这使主流程从：

```text
Analysis → Input → Precheck → Task Builder → Task → Monitor
```

收敛为：

```text
Analysis / Compute Workbench
  工况 → 输入 → Solver → Precheck → Submit → Monitor
```

## 11. Monitor 与结果入口闭环

新增：

```text
GET /api/tasks/{task_id}/workflow-status
```

它把 Task 内部状态转换为工程语义：

- 哪个分析；
- 哪个 Analysis Revision；
- 哪台电机；
- 哪个 Design Revision；
- 哪个 Run Configuration；
- 多少 Case；
- 完成/失败/可用结果数；

`analysis/monitor.js` 在现有 Live Monitor 顶部加入这一摘要，并提供：

- 返回当前分析与计算；
- 查看 Task 详情；

所以“计算已经完成但不知道去哪里”“Monitor 只显示 Task ID，看不出算的是什么版本”这类问题在流程层得到解决。

## 14. V0.67 的完成度判断

### 已完成

本版本可以认为已经完成 **Studio 侧 Analysis / Compute Workflow Closure**：

- Analysis 设置有唯一执行入口；
- 工况、物理输入、求解设置在一个执行上下文中确认；
- Precheck 有唯一普通流程所有者；
- Precheck evidence 与不可变 Revision Pair 绑定；
- 多窗口 stale revision 不会静默错算；
- Submit 生成不可变 Run Configuration；
- Task 创建具备幂等保护；
- Monitor 有完整工程血缘；
- 结果入口与 Task 状态相连；
- 六个步骤可深链接和刷新恢复；
- Legacy Task Builder 退出普通工作流。

### 尚未完成的原生资格

当前 Linux 构建环境没有目标 Windows Motor-CAD 2026R1 GUI、许可证和真实本机材料/模板环境，因此以下内容没有标记为“已完成验证”：

- 真正启动 Motor-CAD 2026R1；
- 目标安装上的 Automation Parameter Names 全量一致性；
- 真实 BPM/SPM/IPM/AFPM 模型打开；
- 真实多工况 speed/current/voltage/phase 应用；
- 真实材料/绕组向 Motor-CAD 模型写入；
- `do_magnetic_calculation` 长时运行；
- steady/transient thermal 真实运行；
- Motor-CAD Lab 建模和 operating point 真实运行；
- Cancel / process ownership / license release；
- 原生 FEA 和结果输出完整性；
- Windows 125% / 150% DPI 下完整流程视觉验收。

Release Manifest 因此明确保持：

```text
studio_implementation_completion_percent = 100
native_motorcad_workstation_qualification_percent = 0
```

这里的 100% 仅表示 **V0.67 既定 Studio 实现范围已经闭环**，不等于真实 Motor-CAD 工程资格已经通过。

## 15. V0.68 应如何推进

V0.68 应严格进入 **Motor-CAD Native Parity Qualification**，不再大规模扩展 UI。

建议工作站验收按四个基准模型开展：

```text
BPM / SPM / IPM / AFPM
```

每个基准至少验证：

1. 打开真实 Motor-CAD 模型；
2. Studio Design Revision 参数逐项写入；
3. 几何与 Motor-CAD 原生图对比；
4. 绕组槽号、匝数、支路、层数和相序对比；
5. 材料名称、数据库来源、B-H/退磁数据对比；
6. Analysis Revision 的工况逐点进入 Motor-CAD；
7. Solver settings 与配方 native automation 字段逐项记录；
8. Precheck 与真实 Motor-CAD 模型检查结果一致；
9. Submit → Motor-CAD calculation 的完整 RPC/进程生命周期；
10. Cancel/stop/异常后的 Motor-CAD 实例和许可证释放；
11. Task/Case/Run Configuration 与原生输出一一对应；
12. 结果曲线、FEA、热结果与 Motor-CAD GUI/导出文件做一致性核验。

通过这些测试后，才能把对应模板/配方从当前的“实现可用”提升到真正的 `NATIVE_QUALIFIED`。

## 16. 本轮结论

V0.67 的关键成果不在于增加一个“计算页面”，而在于把已有 Design、Analysis、Input、Solver、Precheck、Run Configuration、Task、Monitor 和 Results 重新连接成一条具有明确状态所有权和不可变版本边界的工程流程。

此前最容易产生误操作的位置——重复 Precheck、旧页面提交新 Analysis Revision、Task Builder 二次配置、Precheck 证据漂移、Monitor 看不到版本血缘——均建立了明确的后端约束和前端状态处理。

因此后续不建议继续在 Analysis 页面上增加新的流程层。V0.68 应进入真实 Windows + Motor-CAD 2026R1 的原生一致性验证，以真实计算证据关闭 Studio 实现与 Motor-CAD 工程执行之间的最后边界。
