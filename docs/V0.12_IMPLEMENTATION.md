# MotorCAD Studio V0.12 Implementation

## 1. Version objective

V0.12 is the **Production Qualification & Runtime Hardening** iteration. It does not introduce AI and does not claim Motor-CAD production qualification without a real Windows/Motor-CAD/licence workstation. Its purpose is to close the highest-risk gaps found in the V0.11 audit: engineering-lineage-safe project deletion, unified real-time channel behaviour, explicit template qualification, material mapping verification, operator/expert separation, parameter edit ergonomics, and reproducible diagnostics.

## 2. Project lifecycle

Projects now have `ACTIVE` / `TRASHED` state and `deleted_at`. Normal deletion is a soft delete. Design, revision, scenario, experiment, task, case, result, artifact, dataset and dataset-member lineage remain intact. The UI exposes a Trash panel with restore. Physical purge is a separate developer operation and refuses to remove projects with task history unless `purge_history=true` is explicitly requested.

This avoids a V0.11 failure mode where deleting an engineering project could detach historical tasks from their original Project/Design context.

## 3. Unified real-time transport

`static/realtime.js` introduces `RealtimeChannel` and is shared by:

- `/api/system/stream`
- `/api/tasks/{task_id}/stream`
- `/api/logs/stream`

The state machine is:

```text
CONNECTING -> CONNECTED -> RECONNECTING -> POLLING -> OFFLINE
```

After three consecutive EventSource failures, the channel closes SSE and switches to a five-second HTTP polling fallback. System polls `/api/system/metrics`, task monitoring polls `/api/tasks/{id}/monitor`, and logs poll `/api/logs`. This removes the permanent “reconnecting” state that previously remained possible for Task and Log streams even after the System stream had been hardened.

## 4. Production qualification

A new isolated `MotorCADQualificationRunner` executes qualification in a spawn child process. It has an independent timeout and process-tree termination path so a failed Motor-CAD launch, RPC connection or licence checkout cannot block the FastAPI service process.

The qualification contract supports progressive levels:

```text
Level 0: environment unavailable / qualification failed
Level 1: Motor-CAD process and RPC usable
Level 2: target template/model loads
Level 3: runtime parameters/materials/geometry verified
Level 4: real solver smoke calculation and result extraction succeed
```

`MotorCADSolverAdapter.qualify_template()` currently verifies:

1. PyMotorCAD import and target executable selection;
2. Motor-CAD instance creation and RPC;
3. local MOT or registered template load;
4. runtime parameter discovery;
5. optional parameter write/readback;
6. component material application/readback;
7. geometry validation;
8. optional EMag or steady-thermal smoke calculation;
9. Motor-CAD message retrieval;
10. controlled Motor-CAD shutdown.

The qualification path does not create a Task/Case and therefore can be used as an environment/template acceptance test.

## 5. Material verification semantics

V0.12 distinguishes three concepts:

```text
Studio public material catalog
        !=
Motor-CAD material database entry
        !=
validated physical material curve
```

`POST /api/materials/validate` only checks the Studio catalog and explicitly reports `motorcad_database_verified=false`. Real Motor-CAD availability is confirmed only when qualification or a real task successfully calls the Motor-CAD material APIs and reads the assignment back.

The built-in material catalog therefore remains a selection convenience, not a replacement for supplier B-H, loss, demagnetisation, thermal or temperature-dependent curves.

## 6. Operator / engineering / expert / developer modes

The header now exposes four UI complexity levels:

- **Basic**: normal single-design operation with advanced roles hidden;
- **Engineering**: engineering parameter roles, task design and standard analysis controls;
- **Expert**: reviewed Motor-CAD Automation parameters and advanced solver controls;
- **Developer**: raw Automation text, API registry and destructive maintenance functions.

Expert and developer content is hidden structurally via CSS classes, not merely visually renamed.

## 7. Parameter editing

The Engineering Parameter Editor now supports:

- search and changed-only filters inherited from V0.11;
- Fixed / DOE / Optimization role per parameter;
- lower/upper bounds for DOE/optimization roles;
- synchronization into the existing DOE variable table;
- local min/max validation state;
- an edit history with Undo / Redo;
- `Ctrl+Z`, `Ctrl+Y`, and `Ctrl+Shift+Z` shortcuts outside input controls.

The Basic mode hides the parameter-role controls to avoid unnecessary complexity for single-case operation.

## 8. Experiment Wizard

The task builder includes a wizard that asks for engineering intent before algorithm terminology:

```text
Evaluate current design        -> Single
Study one parameter            -> Sweep
Explore multiple parameters    -> Latin Hypercube
Find multi-objective tradeoff  -> NSGA-II
```

The existing detailed controls remain available after the wizard chooses a mode.

## 9. Reviewed Automation metadata

`config/automation_parameter_metadata.yaml` contains reviewed metadata for high-frequency Motor-CAD Automation controls used in the official/example workflow. Entries include:

- Chinese and English labels;
- Chinese engineering description;
- category;
- risk level;
- source;
- review status.

Imported Automation Parameter Names are enriched from this registry. Unknown native variables remain explicitly `reviewed=false`; the GUI does not present keyword-generated text as authoritative documentation.

## 10. i18n migration

V0.12 adds a key-based `tKey()` resource foundation and reverse mappings for historical English labels that were embedded in the original workspace. This coexists with the V0.11 DOM translation layer to keep the current application stable.

This is an intermediate migration. A future release should remove literal user-facing strings from `app.js/index.html` and use locale keys everywhere, including API status/error-code localization and date/number formatting.

## 11. Diagnostics

The diagnostic ZIP now includes `environment.json` with:

- Studio version;
- OS and Python version;
- target Motor-CAD version;
- configured/selected Motor-CAD executable;
- registry hashes;
- model policy;
- strict mapping state;
- instance-reuse configuration;
- licence-pool snapshot.

It complements the existing structured logs, text logs, audit logs, filtered diagnostics, task state and per-Case solver logs.

## 12. Known boundaries

V0.12 deliberately does not claim completion of the following:

- i5/e9/e14 Level-4 qualification on a real Motor-CAD workstation;
- full Studio-catalog-to-Motor-CAD-material-database synchronization;
- complete key-based Chinese/English migration;
- real Lab efficiency/loss maps for all curated templates;
- template-specific FEA/3D Graph Viewer name calibration;
- long-lived MotorCADSessionPool;
- mesh/vector field rendering beyond the existing Map2D result contract.

These are production-validation/data-coverage tasks rather than missing control-plane architecture.
