# MotorCAD Studio V0.21.0 — 工程领域模型与可追溯运行配置

## 1. 本轮目标

V0.20 已经解决了项目优先、路由、五步仿真向导、模型门禁和 Motor-CAD 原生诊断等主要操作问题。继续检查实际界面后，仍存在一个底层矛盾：Design Revision、Scenario、求解设置、输出设置和 Task 的职责边界不够稳定。长期设计参数与运行点混在同一参数集合时，用户很难回答三个关键问题：

1. 当前电机“设计本体”到底是什么；
2. 本次计算改变的是设计、工况还是求解器；
3. 一个历史 Task 如何精确复现。

V0.21 将工程对象边界收敛为版本化领域模型，并让 Task 成为纯执行实例。

## 2. V0.21 目标领域模型

```text
Project
├─ Design
│  └─ Design Revision (immutable)
│     ├─ topology
│     ├─ geometry
│     ├─ magnet
│     ├─ winding
│     └─ materials
│
├─ Scenario
│  └─ Scenario Revision (immutable)
│     ├─ shaft speed
│     ├─ current
│     ├─ DC bus voltage
│     ├─ phase advance
│     ├─ ambient / initial condition
│     └─ cooling boundary
│
├─ Solver Profile
│  └─ Solver Profile Revision (immutable)
│     ├─ analysis
│     ├─ quality profile
│     ├─ solver settings
│     ├─ automation overrides
│     └─ timeout
│
├─ Output Profile
│  └─ Output Profile Revision (immutable)
│     └─ requested outputs
│
└─ Run Configuration (immutable)
   ├─ four baseline bindings
   ├─ explicit runtime override deltas
   ├─ full effective execution snapshot
   ├─ content hash
   ├─ traceability status
   └─ snapshot schema version
        ↓
      Task
        ↓
      Case
        ↓
      Result / Dataset
```

核心规则：Design Revision 只描述可长期复用的机器定义；Scenario Revision 描述运行点和边界条件；Solver/Output Profile 独立版本化；Task 提交前冻结 Run Configuration。

## 3. Design / Scenario 边界

### 3.1 Design Revision

新建 Design Rev.1 和后续新 Revision 时，后端仅保存参数注册表中以下类别：

```text
topology
geometry
magnet
winding
```

`shaft_speed_rpm`、`peak_current_a`、`rms_current_a`、`dc_bus_voltage_v`、`phase_advance_deg` 等字段不再进入新的 Design Revision。

### 3.2 Scenario Revision

Scenario 现在正式拥有：

```text
shaft_speed_rpm
peak_current_a
rms_current_a
dc_bus_voltage_v
phase_advance_deg
ambient_temperature_c
initial_temperature_c
initial_condition_mode
cooling_type
coolant_inlet_temperature_c
coolant_flow_rate_lpm
external_air_speed_mps
altitude_m
fixed_temperature_c
```

TaskManager 在生成 Case 前把 Scenario 中的运行点映射回 Motor-CAD 参数集合，因此领域拆分不会导致求解器缺少速度、电流或母线电压。

## 4. Solver Profile / Output Profile

新增数据库实体：

```text
solver_profiles
solver_profile_revisions
output_profiles
output_profile_revisions
```

每个 Project 自动拥有一个默认求解配置和默认输出配置。用户可以：

- 在现有 Profile 上保存新的 Revision；
- 将当前设置另存为新的 Profile；
- 在 Task Builder 中选择历史 Revision；
- 修改后以“当前页临时覆盖”运行，Run Configuration 会记录基线和差异；
- 正式复用前保存为新的版本化配置。

## 5. Run Configuration

### 5.1 为什么引入

以前 Task 同时承担配置与执行，导致“Task 是配置还是运行记录”的语义混合。V0.21 增加独立 Run Configuration。

一个 Run Configuration 包含：

```text
Design Revision baseline
Scenario Revision baseline / inline scenario
Solver Profile baseline / inline solver config
Output Profile baseline / inline output config
runtime overrides
experiment definition
materials
full effective parameter payload
```

### 5.2 内容哈希

冻结快照使用确定性 JSON 编码计算 SHA-256 `content_hash`。Task、结果和 Dataset 可以据此核对配置内容。

### 5.3 基线与覆盖差异

Run Configuration 不会把“修改后的数据”伪装成被引用 Revision 的内容。例如：

```text
Scenario Rev.2
shaft_speed_rpm = 3000

本次运行
shaft_speed_rpm = 3600
```

冻结快照会记录：

```json
{
  "bindings": {
    "scenario": {
      "revision_id": "SRV-...",
      "overrides": {
        "shaft_speed_rpm": {
          "base": 3000,
          "effective": 3600
        }
      }
    }
  }
}
```

这允许工程试算保留灵活性，同时避免历史血缘被误读。

### 5.4 Traceability Status

当前定义：

- `FULLY_VERSIONED`：四个领域对象全部绑定不可变 Revision，且无本次临时覆盖；
- `VERSIONED_WITH_OVERRIDES`：四个领域对象全部绑定版本，但本次执行存在明确覆盖；
- `PARTIAL_INLINE`：至少一个 Scenario / Solver / Output 尚未保存为版本化资产，Run Configuration 保存其完整 inline snapshot。

### 5.5 重算语义

新增：

```text
POST /api/run-configurations/{run_id}/tasks
```

它从不可变快照重新构造 TaskCreate 并建立新的 Task。普通 `/api/tasks` 如果携带已有 `run_configuration_id`，后端会逐项核对有效执行配置；任何差异返回：

```text
RUN_CONFIGURATION_MISMATCH
```

因此一个 Run Configuration ID 不能被错误贴到另一组参数上。

## 6. 冻结时机修复

TaskManager 会根据优化目标和约束自动补充必须提取的输出。V0.21 将这一步提前到 Run Configuration 冻结之前。

正确顺序：

```text
用户配置
↓
补齐目标/约束依赖输出
↓
Task validation
↓
Freeze Run Configuration
↓
Create Task
↓
Generate Cases
```

这样 Task 的 `request_json` 与 Run Configuration 的有效输出集合一致。

## 7. 仿真配置资产页面

新增项目内二级入口：

```text
仿真
├─ 配置资产
├─ 配置计算
├─ 任务记录
└─ 实时监控
```

配置资产页管理：

```text
工况 Scenario
求解配置 Solver Profile
输出配置 Output Profile
运行配置 Run Configuration
```

所有资产页均有正式路由。资产详情进一步支持：

```text
/app/projects/{project}/simulation/assets/{kind}/{assetId}
```

因此可以刷新、复制链接、浏览器前进/后退恢复。

Run Configuration 详情直接显示内容哈希、Traceability Status、四类基线、覆盖差异和完整冻结快照，并提供“按此冻结配置重新计算”。

## 8. 历史数据自然迁移

V0.20 及以前生成的 immutable Design Revision 可能仍包含速度、电流、电压等字段。V0.21 不会原地修改这些历史记录，因为那会破坏旧 Task 的可追溯性。

新增：

```text
GET /api/projects/{project_id}/domain-integrity
```

检查：

- 仍包含 Scenario 域字段的历史 Design Revision；
- 尚无 Run Configuration 的历史 Task；
- 当前 Scenario / Solver / Output 资产数量。

界面会显示领域数据检查条。历史对象继续保留；对旧 Design 进行下一次正式修改并创建新 Revision 时，新版本自然进入 V0.21 领域模型。

为避免旧 Design 中的运行点字段在进入 V0.21 后被模板默认值覆盖，Task Builder 加载旧 Revision 时会识别 `shaft_speed_rpm / peak_current_a / rms_current_a / dc_bus_voltage_v / phase_advance_deg / ambient_temperature_c` 等历史 Scenario 字段，并恢复为当前页面的临时 Scenario。界面明确提示将其保存为新的 Scenario Revision；旧 Design Revision 本身保持不可变。

## 9. Data Factory 血缘增强

每个 Case 数据记录新增：

```text
solver_profile_revision_id
output_profile_revision_id
run_configuration_id
run_configuration_hash
run_traceability_status
run_snapshot_schema_version
```

Dataset manifest 的 lineage policy 升级为：

```text
case_id
+ run_configuration_id/content_hash
+ design/scenario/solver/output revisions
+ input_hash
+ solver/template/registry provenance
```

这为后续 AI/代理模型训练提供更可靠的数据来源区分。

## 10. 数据库变化

Schema Version：`13`

新增：

```text
solver_profiles
solver_profile_revisions
output_profiles
output_profile_revisions
run_configurations
```

`tasks` 增加：

```text
run_configuration_id
```

`run_configurations` 包含：

```text
traceability_status
snapshot_schema_version
```

V0.21 仍沿用现有启动期 `CREATE TABLE IF NOT EXISTS + ensure_column` 兼容升级机制。真正版本化 Migration 应在后续可靠性迭代中替换这一机制。

## 11. UI 细节调整

- Task 参数编辑器重新表述为“设计基线与本次临时覆盖”；

## 14. V0.21 仍存在的架构债务

V0.21 已经把工程对象模型收敛，但实现层仍保留早期版本的集中式结构。当前源码规模约为：`main.py` 1651 行、`task_manager.py` 1271 行、`solvers/motorcad.py` 1480 行、`domain.py` 565 行；前端静态脚本中仍有大量函数声明和约 50 处 `setTimeout`，`operator-flow.js / router.js / workflow.js / v021.js` 仍存在对 `showTab` 或相关行为的分层包装。URL 已经路由化，页面生命周期仍部分依赖旧 Tab/global state 机制。

数据库升级仍采用 `CREATE TABLE IF NOT EXISTS + ensure_column` 的兼容策略；浏览器级 E2E、真实 Windows Motor-CAD Contract Test、故障注入与长时间多 Case soak test 也还没有进入自动验收。因此下一阶段应优先降低页面生命周期和运行时的不确定性，再继续扩展工程功能。

此外还有三项领域层细化空间：

- DOE/优化的 Experiment 当前作为 Run Configuration 的 inline definition 冻结，能够复现，但尚未成为可独立复用的版本化资产；
- `requested_outputs=[]` 仍具有“使用模板推荐输出”的上下文语义，后续可显式增加 `selection_mode=explicit|template_recommended` 并记录 registry/catalog hash；
- 材料目前已纳入 Design 血缘和 override delta，但未来还需要材料数据库 checksum、材料曲线来源与版本，以保证 AI 数据集能够复现相同的 BH/损耗/热物性。

## 15. 下一阶段建议

### P0：V0.22 Frontend Core

V0.20 已经有 URL Router，但页面内部仍保留旧 Tab、全局 `state`、函数覆盖和 `setTimeout` 恢复逻辑。下一步应把页面真正拆成 Route-first 生命周期：

```text
Router
→ Context Resolver
→ Page Controller
→ load(AbortSignal)
→ render
→ bind
→ dispose
```

同时拆分 ES Modules、统一 Store、统一 API cancellation、Key-based i18n。该工作能显著降低异步页面互相覆盖的问题。

### P0：V0.23 Motor-CAD Runtime + Validation Evidence

建立独立 Motor-CAD Session Supervisor，并把检查结果从瞬时 Gate 升级为可追溯 Validation Evidence：

```text
L0 Static Constraints
L1 Native Model Build / Readback
L2 Solver Smoke
L3 Full Solve
L4 Result Quality
```

每份 Evidence 绑定 Motor-CAD 版本、模板哈希、Run Configuration hash、消息日志、参数回读与 Native Snapshot。

### P1：V0.24 Engineering Workbench

建立 Parameter Dependency Graph，把错误映射到具体字段和模型区域：

```text
slot_count
→ slot pitch
→ tooth/slot ratio
→ winding pattern
→ conductors/slot
→ slot fill
→ winding factor
```

模型失败后直接提供“问题参数 -> 影响关系 -> 修复候选 -> 重新检查”。

### P1：V0.25 Reliability

- 版本化数据库 Migration；
- Playwright 浏览器 E2E；
- Windows Motor-CAD Contract Test；
- RPC/License/Worker/DB fault injection；
- 长时间多 Case soak test。

### P2：V0.26 Engineering Decision & AI Data

结果中心升级为 Revision / Run Configuration 决策工作台，支持基准/候选对比、可行性矩阵、Pareto 筛选和“从结果生成下一 Revision”。Data Factory 继续加入 Validation Evidence ID、模型版本和数据质量策略，使数据能够安全用于代理模型与智能设计。
