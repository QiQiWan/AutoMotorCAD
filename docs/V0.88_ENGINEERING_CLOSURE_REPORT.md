# MotorCAD Studio V0.88.0 Engineering Closure Report

Date: 2026-08-23  
Scope: reported HMI/geometry/material/native-validation defects + uploaded runtime diagnostics  
Target native solver: Motor-CAD 2026R1

## 1. Executive conclusion

The uploaded diagnostics show that the repeated native validation failure was not a slot-geometry failure. All four current `MODEL_RUNTIME_CHECK` failures stopped earlier at material binding:

`Conductor = Copper (Annealed) -> pymotorcad set_component_material failed`

The front-end diagnostics then misclassified this as `GEOMETRY` because the route/work-directory contained the word `geometry`. The deeper data-contract defect was that `MaterialConfiguration` discarded `material_provenance`, so a material inherited from the loaded Motor-CAD template was treated as an explicit user assignment and redundantly written back through the generic logical component name `Conductor`.

V0.88.0 closes that chain end-to-end: provenance is preserved, inherited template materials are not rewritten, explicit assignments use native readback/aliases and fail with structured material-stage evidence, and the UI now reports the exact failing stage, component, material and recommended action.

The other eight reported UX/visual defects are also repaired in the source package. Formal Windows native qualification remains pending until this build is executed on the user's licensed Motor-CAD 2026R1 workstation.

## 4. Native material-binding root cause and corrected contract

### Old failing chain

1. A template revision contained `Conductor = Copper (Annealed)` and provenance indicating it came from the template MTT.
2. `MaterialConfiguration` did not declare the provenance/inherited-material fields, so Pydantic discarded them during model validation.
3. Native qualification received only the material name and assumed it was an explicit assignment.
4. The adapter called `set_component_material("Conductor", "Copper (Annealed)")`.
5. Motor-CAD 2026R1 rejected the generic component alias.
6. Qualification exited before native geometry and winding checks.
7. Diagnostics categorized the failure as GEOMETRY because the generic request route included `geometry-check`.

### New contract

- `MaterialConfiguration` preserves `material_provenance`, `inherited_component_materials` and `template_component_materials`.
- `source_kind=template_mtt` is authoritative inheritance: the loaded template already owns this material, so Studio records `template_inherited_no_write` and does not issue a redundant native write.
- Explicit user material assignment first performs native readback. If the native component already has the requested material, it records `already_matched` with no write.
- If a write is required, the component alias registry is tried deterministically. Conductor candidates now include `Copper - Active`, `Copper (Active)`, `Winding Conductor`, `Stator Winding`, and `Conductor`.
- Failure is represented as `MaterialBindingValidationError` with component, material, source kind, candidate native targets, native error list and operator action.
- The UI renders the root stage as `材料绑定` instead of displaying unrelated slot-geometry advice.

This is intentionally fail-closed for an explicitly selected material. Silent fallback to the template would make the design different from what the engineer selected.

## 5. Longitudinal section geometry authority

The corrected RFPM shaft-axis view follows r-z semantics:

- horizontal direction: shaft/axial direction;
- vertical direction: radial direction;
- shaft occupies the centerline;
- rotor iron appears as upper/lower annular section blocks around the shaft, not a solid body through the shaft;
- SPM magnets sit on the rotor outer surface; IPM magnets are embedded in the rotor region;
- the air gap is a filled physical band between rotor envelope and stator bore;
- stator, slot windows and active copper are separated;
- end windings are shown only as short axial-end connections and all winding paths use `fill:none`.

The Studio drawing remains an engineering preview. After native qualification, Motor-CAD geometry/readback remains the final geometry authority.

## 6. Magnet chart data policy

For records containing native sampled magnet B/H arrays, the UI plots those source points directly.

For the supplied `N30UH` record, the available scalar properties include approximately Br=1.125 T, HcJ=1.99 MA/m, mur=1.05, reference temperature 20 °C, valid temperature range 20–180 °C and temperature coefficients. No sampled `BValue_Magnet/HValue_Magnet` array is present in the available source record.

V0.88.0 therefore derives a reference second-quadrant working line at the reference temperature using:

`B(H,Tref) = Br(Tref) + mu0 * mur * H`

and separately plots Br(T) and HcJ(T) from the source coefficients. The UI labels this series as derived. A full magnetization/hysteresis loop cannot be reconstructed reliably from these scalar properties; manufacturer or measured raw curve points are required for that feature.

## 7. Performance and runtime corrections

The two recorded route warnings were about 2.1 s. A supplemental `MCSEngineeringWorkflow.refresh(projectId)` was awaited during route mount even though the route content could already be displayed. V0.88.0 moves this refresh to the background and re-synchronizes the shell only after it finishes, provided the route is still active.

Draft autosave debounce is increased from 650 ms to 1000 ms to reduce PUT churn during continuous numeric editing while preserving route-safe flush behavior.

Native geometry-check calls in the uploaded session took roughly 9.9–10.9 s and stopped at material binding. With redundant inherited material writes removed, the next run should progress into the actual Motor-CAD geometry/winding stages. Native application launch/RPC remains intrinsically expensive and should be handled by worker reuse rather than hidden by the UI.
