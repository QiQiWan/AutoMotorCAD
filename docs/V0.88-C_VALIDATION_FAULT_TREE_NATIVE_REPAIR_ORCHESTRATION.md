# V0.88-C — Validation Fault Tree & Native Repair Orchestration

Release: **MotorCAD Studio 0.88.3 / Schema 44**  
Windows production qualification contract: **0.88-C**

## 1. Goal

V0.88-A qualified the exact Motor-CAD names Studio is allowed to use. V0.88-B proved what geometry, winding and material state the live model actually contains. V0.88-C closes the engineer-facing validation loop by turning native mismatch/unresolved evidence into a deterministic fault tree and a bounded repair plan.

The authority chain is:

`Design Snapshot -> BindingPlan -> live Motor-CAD -> NativeModelSnapshot -> NativeFaultRecord[] -> NativeRepairPlan -> optional explicit safe repair -> fresh NativeModelSnapshot`

The key rule is that repair orchestration cannot invent design intent. It can only resynchronize the current live Motor-CAD session to values already frozen into the exact current BindingPlan.

## 2. Typed fault authority

`NativeValidationFaultTreeAuthorityV1` converts the legacy V0.88-B `fault_tree` rows into `NativeFaultRecord` objects with:

- deterministic `fault_id` and `code`;
- domain and lifecycle stage;
- severity/status and root-cause rank;
- canonical `parameter_ids` and `component_ids`;
- exact native targets when known;
- engineer-facing message and repair hint;
- linked repair-action IDs.

The normalized fault set is hash-anchored. A clean snapshot still has a deterministic hash for the empty fault set.

Representative fault routing:

| Fault | Interpretation | Repair route |
| --- | --- | --- |
| `NATIVE_GEOMETRY_READBACK_DRIFT` | live geometry value differs from frozen design | safe reapply only for explicit READ_WRITE_VERIFIED binding; otherwise parameter editor |
| `NATIVE_GEOMETRY_READBACK_UNRESOLVED` | exact native readback evidence missing | rerun V0.88-A semantic qualification |
| `NATIVE_GEOMETRY_INVALID` | Motor-CAD geometry kernel rejects model | manual Motor-CAD Geometry diagnosis |
| `NATIVE_GEOMETRY_VALIDATION_UNAVAILABLE` | required PyMotorCAD validity API unavailable | verify Motor-CAD/PyMotorCAD API/version |
| `NATIVE_WINDING_PARAMETER_DRIFT` | high-level winding scalar differs | safe reapply only when frozen explicit binding permits it |
| `NATIVE_WINDING_TOPOLOGY_DRIFT` | coil topology/signature differs | safe coil rewrite only for frozen custom-coil authority |
| `NATIVE_WINDING_READBACK_INCOMPLETE` | structured coil evidence missing | inspect generated winding/API |
| `NATIVE_MATERIAL_READBACK_DRIFT` | live component material differs | safe reapply only for explicit writable assignment; inherited material stays confirmation/manual |
| `NATIVE_MATERIAL_READBACK_UNRESOLVED` | material component readback unresolved | requalify semantic component binding |
| `NATIVE_POST_SOLVE_DESIGN_STATE_DRIFT` | solver changed native design state | discard result, reload frozen model, revalidate and rerun |

## 3. Repair safety model

Every `NativeRepairAction` is classified into one of four safety classes.

### `AUTO_SAFE`

Execution is permitted only when all required lineage and authority checks pass. Current executable actions are:

- `REAPPLY_PARAMETER`;
- `REAPPLY_MATERIAL`;
- `REAPPLY_CUSTOM_WINDING`.

The action writes only the target already frozen into the current `MotorCADBindingPlan`, immediately reads back the value/topology and captures a fresh `NativeModelSnapshot`.

### `CONFIRM_REQUIRED`

The action changes or may reinterpret engineering intent and therefore requires the engineer to choose it. Examples include opening the parameter/material/winding editor or reloading a template baseline whose inherited material changed.

### `MANUAL_ONLY`

Studio can diagnose and navigate but cannot safely repair the condition. Examples include native geometry invalidity, missing PyMotorCAD APIs and post-solve design-state mutation.

### `BLOCKED`

The plan cannot be executed because authority or lineage is insufficient.

## 4. Lineage gates

`NativeRepairOrchestratorV1` refuses execution when any of the following is stale or inconsistent:

- `binding_plan_hash`;
- `design_snapshot_hash`;
- RepairPlan binding-plan hash;
- RepairPlan design-snapshot hash.

This prevents a repair generated for Revision A from being applied to Revision B after the engineer changes parameters.

The orchestrator never modifies:

- the source `.mot/.mtt` template;
- Design Draft intent;
- an immutable Design Revision;
- template-inherited material intent.

## 5. Bounded repair lifecycle

The design-time native check supports three policies:

- `suggest` — diagnose only; default;
- `safe_auto` — execute one bounded AUTO_SAFE pass, then run native validation again;
- `manual` — diagnose/navigate without live writes.

The HMI exposes `safe_auto` only through the explicit **“安全修复并重新检查”** control when at least one AUTO_SAFE action exists.

A repair attempt stores:

- before snapshot/design-state hashes;
- selected action IDs;
- per-action write/readback result;
- post-repair native evidence hash and design-state hash;
- final outcome (`REPAIRED`, `PARTIAL`, `FAILED`, `BLOCKED`, `NOOP`);
- verification state and errors.

Repair history survives subsequent native validation and post-solve captures. This is required so formal production qualification cannot accidentally lose evidence that a repair occurred.

## 6. Formal qualification boundary

Formal Native Closure does **not** auto-repair. The post-solve evidence must satisfy:

- V0.88-A semantic profile `QUALIFIED`;
- V0.88-B `NativeModelSnapshot.status == QUALIFIED`;
- `phase == post_solve`;
- stable snapshot and design-state hashes;
- V0.88-C `NativeRepairPlan.status == CLEAN`;
- typed fault set empty;
- non-empty RepairPlan and fault-tree hashes;
- repair-attempt count exactly zero.

The Windows production contract is therefore upgraded to `0.88-C` and introduces the release gate `native_repair_orchestration_authority` and scenario gate `native_repair_orchestration_clean`.

## 7. API/HMI surface

Design-time geometry/native-check responses now expose:

- `native_fault_tree`;
- `native_repair_plan`;
- `native_repair_plan_hash`;
- `native_repair_attempts`;
- root-cause typed fault;
- parameter/component locators.

Native Closure evidence additionally exposes:

- `/api/native-closure/runs/{run_id}/native-model-snapshot`;
- `/api/native-closure/runs/{run_id}/native-repair-plan`.

The validation UI renders the root fault first, provides direct parameter/component navigation and only displays the safe-repair button when the authority marks an action AUTO_SAFE.

## 8. Hot-route performance closure

During V0.88-C regression testing, Standard Validation materialization exposed a separate but consequential hot-route defect: each analysis capability check rebuilt the registered PM plugin contract, and `BuiltinPMFamilyPlugin.qualification_profiles()` reparsed `motor_topologies.yaml` repeatedly. A single materialization could spend tens of seconds repeatedly parsing the same static YAML.

V0.88-C therefore also:

- caches immutable registered `PluginContractSnapshot` objects for the registry lifetime;
- caches PM `template_overrides` when the plugin is constructed;
- keeps revalidation on explicit register/replace only.

This removes repeated YAML/provider reconstruction from native-qualification/status paths without changing engineering semantics.

## 9. Production claim

The local build verifies the fault authority, repair safety rules, lineage rejection, repair-history preservation, HMI/API wiring and Windows fail-closed contract with simulated PyMotorCAD objects and local regression tests.

The build environment cannot launch the user's licensed Windows Motor-CAD 2026R1 workstation. Therefore live SPM/IPM/AFPM/IM V0.88-C qualification remains pending until the Windows qualification runner produces and imports immutable target-workstation evidence.
