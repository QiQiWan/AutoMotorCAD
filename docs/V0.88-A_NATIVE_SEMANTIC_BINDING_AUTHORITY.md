# V0.88-A — Native Semantic Binding Authority

> Layer note: this document specifies the active V0.88-A semantic authority retained inside the current 0.89.3 architecture. The formal workstation qualification contract has advanced to **0.88-F**; section 11 below records the V0.88-A release-time contract for provenance.

Release: **MotorCAD Studio 0.88.1**  
Target: **Motor-CAD 2026R1 / PyMotorCAD 0.8.8**

## 1. Purpose

V0.88-A closes the semantic gap between Studio's canonical engineering names and the exact string names accepted by a live Motor-CAD model.

Before this release, a binding such as `air_gap` or `Conductor` could carry several historical candidates and the runtime would retry them until one happened to work. This was useful during early integration, but it made production behaviour dependent on alias order and could misclassify a material binding failure as a geometry failure.

V0.88-A introduces one versioned authority chain:

`Canonical semantic ID -> configured discovery candidates -> live API qualification -> source-scoped semantic profile -> frozen BindingPlan -> write/readback evidence`

The live semantic profile is the authority used by production binding plans. Configuration candidates remain discovery/fallback metadata.

## 2. Authority levels

| Level | Evidence | Meaning | Allowed use |
|---|---|---|---|
| L0 | versioned YAML candidate | reviewed discovery candidate | development fallback only |
| L1 | `get_datastore()` / geometry-tree evidence | supplementary discovery | may reorder/suggest a candidate; cannot qualify it |
| L2 | successful `get_variable()` or `get_component_material()` | exact live readable name | read-only consumers |
| L3 | read -> same-value set -> readback | exact live readable/writable name | write authority |

`READ_WRITE_VERIFIED` is required before a cached parameter/component name can replace the candidate list in a write plan. A `READ_VERIFIED` profile can accelerate read-only inspection but is never promoted to write authority.

## 3. Cache scope and invalidation

Profiles are stored below:

`<runtime>/native_semantic_bindings/<Motor-CAD target>/<template_id>.json`

A profile is accepted only when all of these remain compatible:

- Motor-CAD target version;
- native binding contract version;
- template ID;
- model-source fingerprint.

The model-source fingerprint includes the template version, active source type, registered-template name, local MOT SHA-256 when present, source MTT SHA-256 when present, and source verification state. A template/source change therefore invalidates the profile automatically.

V0.88-A binding contract version is `motorcad-2026R1-v2`.

A read-only probe can create an initial L2 observation when no profile exists. Once a
source-compatible L3 profile exists, later read-only inspection is deliberately not
allowed to overwrite it. A new write-verification run may replace the profile so that
real Motor-CAD regressions remain visible.

## 4. Parameter authority

The profiler reads the versioned parameter schema and probes only reviewed Motor-CAD candidates. If `get_datastore()` exposes a normalized equivalent name, the exact datastore spelling is tried first; it still has to pass the live `get_variable` and same-value `set_variable` roundtrip before becoming write authority.

For example, a configured candidate set:

`air_gap -> [Airgap, Air_Gap]`

may resolve on the workstation to:

`air_gap -> [Air_Gap] / READ_WRITE_VERIFIED`

Subsequent BindingPlans carry only `Air_Gap`, so the solver no longer retries `Airgap` on every Case.

## 5. Material component authority

Motor-CAD component material assignment requires the exact component name accepted by the Materials API. V0.88-A qualifies configured component candidates with:

`get_component_material(component) -> set_component_material(component, current_material) -> get_component_material(component)`

The same-value write proves writability while preserving engineering intent.

Two execution policies are now explicit:

- `inherit_readback`: a material inherited from the loaded template is read back only. The executor never rewrites it merely to prove an alias.
- `write_readback`: a user-assigned material is written only to live-qualified native component names and is read back after assignment.

This specifically closes the field failure where Studio attempted `set_component_material("Conductor", "Copper (Annealed)")` even though the loaded 2026R1 template already carried the conductor material under a different native component name.

The mapping is intentionally one-to-many when the native template requires it. For
example, canonical `Stator Lamination` may qualify both `Stator Lam (Back Iron)` and
`Stator Lam (Tooth)`. The exact qualified set is frozen in the profile and an explicit
material change is applied only to that set.

## 6. Native Closure integration

A Native Closure run now performs V0.88-A semantic qualification immediately after loading the Motor-CAD model and before applying the design BindingPlan.

Sequence:

1. load the exact MOT/registered template;
2. probe live parameter/component semantics using same-value roundtrip;
3. persist `MotorCADSemanticBindingProfile`;
4. write an evidence copy to `native_semantic_binding_profile.json`;
5. rebuild the Native Closure BindingPlan;
6. apply the rebuilt plan using exact qualified names;
7. continue geometry, winding, calculation and result qualification.

This means the first successful Native Closure run can bootstrap the semantic profile and consume it in the same run.

The Native Closure UI shows a separate **语义绑定** state for each Golden template. It is intentionally independent from the overall Native Closure status.

## 7. Fail-closed production policy

`development` mode may still use versioned candidates when a profile is missing. This keeps onboarding and diagnosis possible.

`validation` and `production` modes now reject a normal solve before Motor-CAD write operations when the current template does not have a compatible `QUALIFIED` semantic profile. The error includes the template, current authority state and the required operator action.

This prevents a production Case from silently falling back to alias guessing.

## 8. API

- `GET /api/motorcad-native-binding/catalog`
  - binding version and mapping policy;
  - semantic authority policy;
  - current Golden profile summary.
- `GET /api/motorcad-native-binding/semantic-authority`
  - Golden-template qualification summary.
- `GET /api/motorcad-native-binding/semantic-authority/{template_id}`
  - full compatible profile and profile hash;
  - returns 404 when no source-compatible profile exists.

## 9. Standalone Windows qualification

Use the standalone runner when semantic qualification must be performed before a normal Native Closure campaign:

```bat
python scripts\qualify_native_semantic_bindings.py --fail-on-partial --visible
```

By default it qualifies the Golden SPM/IPM/AFPM templates:

- `i5_Industrial_SPM_Servo_Tooth_Wound`
- `e9_eMobility_IPM`
- `e14_eMobility_AFM`

Read-only diagnosis is available with `--read-only`. A read-only profile never becomes write authority.

The aggregate JSON/Markdown report is written under:

`data/runtime/native_semantic_bindings/qualification/`

## 10. Acceptance criteria

V0.88-A code closure requires:

1. semantic profile schema and cache are versioned;
2. stale model-source profiles are rejected;
3. parameter writes use only `READ_WRITE_VERIFIED` cached names;
4. template-inherited materials perform zero material writes;
5. explicit material assignment uses only the authority-resolved native component names when a qualified profile exists;
6. Native Closure automatically probes and re-freezes its plan;
7. validation/production normal solves fail closed without a qualified semantic profile;
8. the Golden profile summary is visible through API/UI;
9. local regression/static gates pass;
10. the Windows production matrix requires a semantic-qualified profile/hash for every representative native scenario;
11. real Windows + licensed Motor-CAD evidence remains explicitly pending until executed on the target workstation.

The current Windows production qualification contract is `0.88-A`. Its formal release
gate now contains `native_semantic_authority`, and each SPM/IPM/AFPM/IM scenario must
carry `native_semantic_binding_qualified=true` plus a non-empty
`native_semantic_binding_profile_hash`. This prevents an older Native Closure result
from satisfying the current release solely because geometry/solver execution passed.

## 11. Production boundary

The local build environment cannot launch the user's licensed Motor-CAD 2026R1 workstation. Therefore V0.88-A can establish and test the authority mechanism, cache invalidation, planner/executor behaviour and UI/API contracts locally, but it cannot legitimately claim the three Golden profiles as `QUALIFIED` here.

The production gate is satisfied only after the Windows runner or Native Closure produces live L3 evidence for the target workstation/model sources.

## 12. Current integration

V0.88-B has implemented **Native Geometry & Winding Readback Authority** on top of this semantic layer. `NativeModelSnapshot` now compares canonical Design state with live Motor-CAD topology, geometry, winding and material readback using the V0.88-A exact-name authority. See `V0.88-B_NATIVE_GEOMETRY_WINDING_READBACK_AUTHORITY.md` for the current post-validation/post-solve authority and Windows `0.88-C` qualification contract; V0.88-C adds typed validation faults and bounded repair orchestration above this layer.
