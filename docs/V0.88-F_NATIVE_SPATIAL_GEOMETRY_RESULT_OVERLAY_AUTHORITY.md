# V0.88-F — Native Spatial Geometry & Result Overlay Authority

Release: **MotorCAD Studio 0.88.6 / Schema 45**  
Windows qualification contract: **0.88-F**

## 1. Purpose

V0.88-E reconciled Design Intent with canonical Motor-CAD readback for engineer-facing visualization. It still reconstructed geometry from canonical scalar parameters. V0.88-F introduces a separate spatial authority so the product can distinguish an engineering reconstruction from geometry that was actually returned by Motor-CAD.

Two authorities are added:

- `NativeSpatialGeometryAuthorityV1`
- `NativeSpatialResultOverlayAuthorityV1`

The first freezes live GeometryTree region boundaries into the native model state. The second binds those boundaries to native FEA values from the exact same solved Case.

## 2. Spatial geometry authority

`capture_native_spatial_geometry()` consumes `get_geometry_tree()` from the live Motor-CAD session. For every bounded drawable Region it preserves:

- region name/type/material;
- parent, duplication count/angle and singular state when exposed;
- ordered Line/Arc entities;
- Line start/end coordinates;
- Arc start/end/centre/radius;
- region/global XY bounds;
- source/API errors and truncation flags;
- stable `content_hash` and Design/BindingPlan/model-source lineage.

The exact Line/Arc primitive parameters are evidence. `display_points` for an Arc are deterministic sampled points used only for SVG display. GeometryTree entities are expected to be ordered around the Region; V0.88-F therefore preserves entity order rather than re-fitting a new outline.

Status is fail-visible:

- `COMPLETE` — drawable regions exist, entity capture is complete, no truncation/incomplete primitive;
- `PARTIAL` — some native boundaries exist but evidence is incomplete/truncated;
- `UNAVAILABLE` — no drawable GeometryTree boundary could be captured.

The spatial-geometry hash is included in `NativeModelSnapshot.design_state_hash()`. A native region-boundary change can therefore invalidate post-solve design-state equality.

## 3. Native result overlay authority

The result overlay contract accepts only:

1. a `post_solve` `QUALIFIED` NativeModelSnapshot;
2. a `COMPLETE` spatial geometry capture from that snapshot;
3. a normalized native FEA manifest from the same Case;
4. matching BindingPlan, Design Snapshot, model-source, native design-state and spatial-geometry hashes.

The native FEA manifest is bound after the final post-solve readback. This prevents an earlier FEA export from being attached to a later/native-mutated geometry without detection.

## 4. Coordinate alignment

V0.88-F does not silently infer a coordinate transform. It compares the native FEA coordinate envelope with the GeometryTree envelope.

- `CONFIRMED` — at least 85% of the FEA envelope area lies inside the captured geometry envelope;
- `PARTIAL` — 35–85%; formal overlay blocked;
- `MISMATCH` — below 35%; formal overlay blocked;
- `UNVERIFIED` — one side lacks usable bounds; visible warning and formal gate remains unqualified.

The coordinate-system unit is stored as `SOURCE_NATIVE_UNVERIFIED` until the licensed target workstation proves a stable unit contract for all supported analysis domains.

## 5. No-fabrication field rendering

The result viewer follows a strict rule:

- if the Motor-CAD FEA export contains real node IDs plus element connectivity, Studio may draw those native elements and apply the exported element field value;
- if connectivity is unavailable, Studio draws exported native points only;
- Studio does not create Delaunay triangles, guessed mesh edges, smoothed interpolation or a synthetic contour merely to make the field look continuous.

The overlay contract records `interpolation_policy` as `native_connectivity_only` or `NO_INTERPOLATION`.

## 6. HMI behavior

### Design workbench

The radial/native geometry view adds a Motor-CAD GeometryTree boundary card containing exact native region boundaries and spatial hash. This is separate from the topology-specific engineering reconstruction so provenance remains obvious.

The longitudinal/axial section is still an engineering reconstruction from native scalar readback. The current XY GeometryTree does not by itself prove an exact axial section, so V0.88-F does not label that section as exact native spatial geometry.

### Result workbench

Native FEA evidence now exposes:

- spatial authority status;
- render mode;
- coordinate-alignment status;
- spatial-geometry hash;
- overlay hash;
- native-boundary visibility control;
- native-mesh visibility control when connectivity exists;
- blockers when native spatial reconciliation cannot be qualified.

A blocked spatial contract does not hide raw native FEA evidence. Engineers can still inspect the exported points; the UI simply refuses to present them as a qualified geometry-aligned overlay.

## 7. API and artifacts

New API:

`GET /api/cases/{case_id}/spatial-overlay`

The existing FEA evidence endpoint also returns the bounded overlay summary and URL.

New solve artifact:

`native_fea/native_spatial_overlay_contract.json`

The native FEA manifest stores a bounded summary while the full GeometryTree payload remains in the dedicated spatial contract/native snapshot evidence.

## 8. Formal Windows qualification

Contract **0.88-F** adds the release gate:

`native_spatial_geometry_result_overlay_authority`

Every representative SPM/IPM/AFPM/IM scenario must also provide:

- `native_spatial_overlay_qualified = true`;
- non-empty `native_spatial_overlay_hash`;
- non-empty `native_spatial_geometry_hash`;
- `native_spatial_coordinate_alignment = CONFIRMED`.

The release gate is fail-closed. Local Fake/PyMotorCAD tests do not satisfy target-workstation evidence.

## 9. Production boundary

The current build environment cannot launch the licensed Windows Motor-CAD 2026R1 workstation. Therefore V0.88-F code contracts, lineage, browser rendering and qualification logic can be locally verified, while real SPM/IPM/AFPM/IM spatial qualification remains pending.

The following claims remain deliberately outside V0.88-F until live API evidence proves them:

- pixel-identical Motor-CAD CAD viewport reproduction;
- exact axial/longitudinal spatial section from the XY GeometryTree alone;
- inferred coordinate-unit conversion across every electromagnetic/thermal/mechanical result type;
- synthetic continuous contours when native element connectivity is absent.

## 10. Follow-on

A useful next layer is **Native Coordinate Calibration & Cross-Physics Spatial Authority**: explicitly qualify units, origins, axis orientation and transforms for electromagnetic, thermal and mechanical result domains, then bind probes/regions across those domains with reproducible spatial transforms and workstation evidence.
