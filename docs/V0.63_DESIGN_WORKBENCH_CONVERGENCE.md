# MotorCAD Studio V0.63.0 Design Workbench Convergence

## 1. Iteration objective

V0.60.1 fixed concrete geometry, winding, material, refresh and navigation defects. V0.62 then introduced exact design deep links, persistent Design Drafts, explicit Analysis-to-Revision pinning and material provenance. The remaining risk was architectural: the read-only viewer, editable workbench and router still carried overlapping copies of design-view state, and historical version scripts could independently re-apply preferred views or layout rules.

V0.63 establishes a stable design-state boundary before continuing feature growth. The release targets five failure classes:

1. transient view changes after async refresh or route restoration;
2. different stage/sub-view semantics in read and edit modes;
3. compressed design canvas caused by side panels competing for width;
4. duplicate primary actions around Revision creation and editing;
5. route-context type errors caused by DOM events being treated as page runtime contexts.

## 2. Shared design state

A new `static/design/store.js` module exports `MCSDesignStore`. It holds the current Project, Motor Design, Design Revision, read/edit mode, design sub-view, selected parameter, current workbench data, Draft dirty count and Draft save state.

The router writes route identity into the store before page mounting. The viewer and editor mirror their compatibility state through the same store. A store change emits `mcs:design-state`, allowing final header and workflow normalization to occur through explicit lifecycle events instead of arbitrary DOM observation.

The intended ownership chain is:

```text
URL route
   |
   v
MCSDesignStore
   |--------------------|
   v                    v
read-only viewer     Draft editor
   |                    |
   `------> shared navigation
```

The URL remains authoritative for reload/back/forward identity. The store is the in-session design UI boundary. Renderer-local state remains only as a compatibility layer until V0.64 migration.

When the Design ID or Revision ID changes, the store clears stale loaded data, selected parameters, Draft dirty count and Draft status unless the incoming context explicitly supplies replacements. This prevents a fast route transition from exposing state that belongs to the previously opened motor.

## 3. Shared stage and next-step semantics

`static/design/navigation.js` exports `MCSDesignNavigation`. Both the read-only viewer and Draft editor now generate their design navigation from the same four engineering stages:

1. Geometry;
2. Winding;
3. Materials;
4. Design Validation.

Sub-views remain contextual: radial/assembly views under Geometry, winding connection/slot definition under Winding, component material assignment under Materials and model/native evidence under Validation. Revision comparison remains an auxiliary tool and is no longer represented as a normal design stage.

The same module also supplies deterministic next-step transitions. In edit mode the final Validation step resolves to `Save new Design Revision`; in read mode the final step resolves to Analysis Inputs.

## 4. Route-before-render anti-flash repair

The previous viewer could render its preferred design view while an async route restoration was still being applied. This explains the visible pattern where Winding appeared selected briefly and then the page jumped to a section view.

V0.63 mirrors the parsed design route into `MCSDesignStore` before workspace mount. During viewer decoration, view resolution now uses:

1. explicit requested view;
2. exact routed/store view;
3. preserved local view;
4. template preferred/default view.

The previous preferred-view fallback therefore cannot overwrite an already resolved exact route during refresh or browser history navigation.

## 5. Engineering workbench layout

The Draft editor is reorganized by `design-v063.css`.

### Wide desktop

```text
+----------------+-----------------------------+----------------------+
| parameter tree | visual model / design view | parameter inspector  |
+----------------+-----------------------------+----------------------+
| diagnostics / selected part / evidence                              |
+---------------------------------------------------------------------+
```

The parameter inspector is sticky, so an engineer can tune values while retaining model context. Diagnostics span below the primary work area instead of consuming a permanent third side column.

### Medium desktop

Below 1500 px, the tree and visual model remain side-by-side and the parameter editor moves below them. This protects the geometry/winding canvas from being squeezed to an unusable width.

### Narrow window

Below 1050 px the workbench becomes one column. The next-step control and object header also stack, preventing root-page horizontal scrolling.

These are component-level decisions for the Design Workbench; they avoid using browser viewport breakpoints alone to force all project pages into the same geometry.

## 6. Read-only Design object hierarchy

The Design header now emphasizes the engineering object rather than internal IDs:

- motor design name;
- immutable Revision number;
- motor type label;
- current design stage.

Technical Design ID, template ID and content hash move into an expandable technical-information detail.

Only one primary action remains in the default header: `Edit Design`. `Revision history` is secondary. Direct Revision cloning remains available inside the opened history rail, which prevents the user from having to interpret several equally prominent actions that all appear to create a new Revision.

## 7. Draft editing continuity

V0.62 persistent Draft behavior is retained and integrated with the shared store:

- parameter/material changes update shared dirty state;
- selected parameter is mirrored into the store;
- active design view is mirrored and persisted with Draft state;
- leaving edit mode switches the store back to read mode;
- stale-base and conflicting-Draft safeguards remain active;
- final next-step action in Design Validation invokes the existing immutable Revision save flow.

This preserves the important engineering contract that a saved Design Revision is immutable while still allowing browser-refresh-safe iterative editing.

## 8. Systemic route-context hardening

A page runtime route context exposes an `active()` function. Previous code sometimes passed a DOM `MouseEvent` into a function that expected this context; calling `routeCtx.active()` then produced the repeated error:

```text
routeCtx.active is not a function
```

V0.63 adds `MCSPageRuntime.isContextActive(context)`:

- no context: active;
- context without a callable `active`: rejected;
- valid context: call `active()` in a protected block.

All direct `routeCtx.active()` guards in the static application scripts were replaced with the type-safe runtime guard. The contract verifier additionally rejects any reintroduction of the unsafe pattern.

## 9. Frontend convergence boundary

V0.63 deliberately avoids another global MutationObserver. The static application retains exactly one observer for dynamic i18n translation. Design-state synchronization uses explicit route/workspace/store events.

The release still contains legacy renderer debt. V0.24 and V0.31 remain loaded because they contain mature geometry, winding, parameter-editor and evidence rendering. V0.63 moves state/navigation ownership away from them without performing a high-risk full rewrite in one release.

V0.64 should physically migrate renderer responsibilities into stable modules such as:

```text
static/design/
  store.js
  navigation.js
  workbench.js
  geometry.js
  winding.js
  materials.js
  validation.js
  parameter-inspector.js
```

After each renderer is migrated, the superseded `v0xx.js` file should be removed from `index.html` rather than covered by another late patch.

## 10. Verification scope

The V0.63 release adds `tests/test_v063_design_workbench_convergence.py` and `scripts/verify_v063_contract.py`. The new contract checks:

- release/index version consistency;
- module load ordering;
- one shared design store;
- one shared design navigation owner;
- viewer/editor use of the shared contract;
- router use of shared current view;
- exact route-before-render preference;
- responsive workbench grid areas;
- one global MutationObserver only;
- zero unsafe direct route-context `active()` calls.

Packaging validation result: 347 pytest tests passed across four isolated batches (79 + 117 + 77 + 74), Python compileall passed, all static JavaScript files passed `node --check`, and 24 JSON plus 23 YAML files parsed successfully. ZIP integrity is checked after final packaging.

## 11. Windows workstation acceptance checklist

The following items require the target Windows + Motor-CAD 2026R1 workstation and should not be marked native-qualified from the Linux packaging environment.

### Navigation and Draft recovery

1. Open a Design Revision directly at Geometry/Radial, refresh, verify the exact view remains selected.
2. Open Winding/Connection, refresh repeatedly and use browser back/forward; verify there is no transient jump to a geometry section.
3. Enter Edit Design, change at least three parameters, refresh and verify Draft recovery, dirty count and active sub-view.
4. Exit editing while preserving Draft, reopen Edit Design and verify the same Draft and selected work area.
5. Save the Draft as a new Revision and verify the previous Revision remains immutable.

### Responsive layout

Verify at a minimum:

- 1366 x 768;
- 1440 x 900;
- 1920 x 1080;
- 2560 x 1440 when available;
- Windows display scaling 125%;
- Windows display scaling 150%.

At each size confirm:

- no root-page horizontal scrollbar;
- geometry/winding canvas is not hidden by the parameter editor;
- inspector controls remain reachable;
- Revision history opens as a secondary rail;
- one primary Edit Design action is visible;
- next-step control is fully visible and does not overlap the visual model.

### Motor-CAD native consistency

For at least one BPM/SPM, one IPM and one AFPM reference template:

1. compare Studio radial/assembly preview topology with the corresponding Motor-CAD model;
2. run Studio deterministic precheck;
3. run Motor-CAD model check;
4. confirm the design Validation page reports the resulting native evidence;
5. verify that changing only the Analysis Definition does not create a new Motor Design Revision.

### Refresh/error regression

1. repeatedly use `Refresh current project` during Design, Analysis and Result pages;
2. confirm no `routeCtx.active is not a function` toast appears;
3. verify duplicated backend failures aggregate into one error presentation rather than multiple identical toasts.

## 12. Recommended V0.64 scope

The next iteration should focus on physical renderer migration and browser-level acceptance rather than adding another version patch file:

1. extract Geometry and Winding rendering from V0.31 into `static/design/geometry.js` and `winding.js`;
2. extract parameter editing from V0.24 into a dedicated inspector module;
3. remove V0.24/V0.31 from the Design path once compatibility tests pass;
4. replace broad `innerHTML` redraws with component-scoped updates where parameter tuning is high frequency;
5. reduce global `window` exports to explicit application services;
6. introduce Playwright/Chromium visual regression for key desktop widths and design routes;
7. add native Windows screenshots as reference artifacts for BPM/SPM/IPM/AFPM geometry parity;
8. continue Material Library snapshot/provenance work so historical revisions remain reproducible after an external Motor-CAD database changes.
