# V0.25 Route-first Frontend Core

## 1. 本轮为什么优先重构前端生命周期

V0.24 已经具备项目、Design Revision、Scenario、Run Configuration、Task、Native FEA、Session Supervisor 和 Motor Model Workbench。继续增加参数面板或可视化会放大一类已经反复出现的问题：页面 URL 看起来正确，但内部仍由旧 `showTab + global state + setTimeout` 恢复工程对象。只要用户快速切换 Project / Design / Revision / Task，旧请求就可能晚于新请求返回并覆盖当前页面。

V0.24 源码审查时约有 55 处 `setTimeout`、8 处 `previousShowTab` 类兼容调用。V0.25 完成后，整个静态前端仍保留 33 处 `setTimeout`，但这些主要用于输入 debounce、初始化等待、Toast/动画和兼容性 UI；核心 `router.js` 为 0 处 `setTimeout`、0 处 `previousShowTab`。路由对象恢复已经完全转为顺序 `await` + `AbortSignal`。

当前保留数据中的最近 24 小时结构化日志包含 193 条记录，其中 10 条 ERROR、9 条 WARNING。聚合后的历史根因主要仍是两类已知工程/历史问题：16 槽绕组整数关系不可行，以及旧版本 Windows Pipe EOF 竞态。它们应该继续作为历史工程证据保留。本轮解决的对象是另一类高频体验问题：过期页面请求、重复页面加载、重复提交和浏览器异常以前很难在诊断包中被准确识别。

## 2. 新页面生命周期

V0.25 的页面切换契约为：

```text
URL / History
      ↓
Router.parse()
      ↓
MCSPageRuntime.begin(route)
      ├─ abort 上一个 Route Context
      ├─ dispose 上一页 listener / timer / stream
      └─ 创建本页 AbortController
      ↓
Context Resolver
      ↓
render-only tab activation
      ↓
Page Controller.mount(route, ctx)
      ↓
load(signal)
      ↓
render / bind
      ↓
MCSPageRuntime.complete(ctx)
```

页面切换时，旧上下文立即执行：

```text
AbortController.abort()
+ clear scoped interval
+ clear scoped timeout
+ remove scoped listener
+ stop page-owned realtime stream
```

因此旧 Project / Design / Task 的响应不能再合法地写入新页面。

## 3. 页面控制器

`static/v025.js` 现在集中管理高频工程页面：

- Project Manager / Project Settings
- Project Overview
- Template
- Design / Revision / Motor Model Workbench
- Simulation Setup
- Simulation Asset
- Task List / Task Detail
- Live Monitor
- Result / Case
- Data Factory
- Issues & Logs
- Runtime / System

Design 深链恢复不再使用“先打开 workspace，再等待 80 ms，再打开 Design，再等 80 ms，再选择 Revision”。新流程严格顺序执行：

```text
loadWorkspace(ctx)
→ openWorkspaceDesign(designId, ctx)
→ selectWorkspaceRevision(revisionId)
→ openRevisionEditorV024(ctx)
```

每一步都检查 `ctx.active()`。

## 4. URL 继续作为工程对象定位符

V0.25 保留 V0.20 以后建立的 durable route，并提升为页面状态的唯一入口：

```text
/app/projects/{projectId}/overview
/app/projects/{projectId}/designs/{designId}
/app/projects/{projectId}/designs/{designId}/revisions/{revisionId}/edit
/app/projects/{projectId}/simulation/setup/{step}
/app/projects/{projectId}/simulation/tasks/{taskId}
/app/projects/{projectId}/simulation/monitor/{taskId}
/app/projects/{projectId}/results/tasks/{taskId}/cases/{caseId}
```

直接刷新、Back / Forward 和复制深链均走同一 `apply()` 路径。路由中的 Project 已删除或进入回收站时，会在任何 Project-scoped API 请求前返回项目管理，避免一条陈旧链接触发一组 404 请求。

## 5. Task 提交幂等

“提交任务经常失败”中有一部分并不发生在 Motor-CAD。网络延迟、用户双击、响应丢失、浏览器重试都可能让前端再次执行同一 POST，旧架构会重复生成 Run Configuration、Experiment 或 Task。

V0.25 增加：

```text
submission_key
submission_hash
```

前端规则：

```text
任务表单保持不变
→ 使用同一个 submission_key

任意输入发生变化
→ 失效旧 key
→ 下一次提交生成新 key
```

后端规则：

```text
首次 POST
→ 归一化 Task intent
→ 计算 submission_hash
→ 冻结 Run Configuration
→ 创建 Task
→ 保存 key + hash

相同 key + 相同 hash
→ 返回原 Task
→ idempotent_replay = true

相同 key + 不同 hash
→ HTTP 409 TASK_SUBMISSION_KEY_REUSED
```

Schema 15 在 `tasks` 上建立 `submission_key` 唯一索引，应用层同时使用提交锁保护 Run Configuration → Task 创建的临界区。这一机制重点覆盖重复点击和“服务端已创建成功但客户端没有收到响应”的重试场景。

## 6. 前端错误进入中央日志

此前诊断包对 Python / Motor-CAD 很详细，但浏览器端路由失败和未处理 Promise 可能只存在于 DevTools。V0.25 新增 `/api/client-events`，以下事件会写入与 Motor-CAD 相同的结构化日志体系：

```text
FRONTEND_ROUTE_FAILED
FRONTEND_ROUTE_SLOW
FRONTEND_UNCAUGHT_ERROR
FRONTEND_UNHANDLED_REJECTION
```

相同错误 10 秒内自动去重，避免日志风暴。问题中心会将其归类为 `FRONTEND`，并保留 route、错误堆栈和关键上下文。

因此后续用户只上传一个诊断包时，可以同时看到：

```text
浏览器页面生命周期
API 请求
Task Engine
Worker
PyMotorCAD
Motor-CAD Native Message
Case Artifact
```

## 7. 实时通道生命周期

Live Monitor 的 Task SSE/轮询已经绑定 Route Context；离开 Task Monitor 后自动停止。

V0.25 同时将 Issues & Logs 的实时日志通道绑定到日志页面。离开日志页会关闭 SSE/RealtimeChannel，避免隐藏页面继续渲染和触发诊断刷新。System health stream继续作为全局运行时状态保留，因为顶部状态栏跨页面使用它。

## 8. UI 行为变化

- 进入项目直接导航 `/overview`，不再先加载 Dashboard / Task / Data Factory 等多个隐藏页面。
- Task、Monitor、Case、Project Settings 等对象点击直接导航工程 URL。
- 路由切换顶部显示 3 px 非阻塞进度条；页面仍可看到上一帧内容，不使用阻塞式浏览器弹窗或全屏 Loader。
- 慢路由超过 2 秒会记录诊断事件，方便后续区分“接口慢”和“页面逻辑错误”。

## 10. 当前仍保留的边界

V0.25 完成的是“Route-first core”，还没有把所有旧 DOM 页面重写成独立 ES Module。现有 `index.html` 仍承载全部页面 section，`app.js / main.py / motorcad.py / task_manager.py` 仍然偏大。33 处剩余 `setTimeout` 中还有初始化和 UI debounce；它们不再用于核心路由对象恢复，但后续仍应逐步替换为显式 lifecycle / debounce utility。

更重要的是，V0.25 不能单独消除真实 Motor-CAD 求解失败。16 槽绕组不可行、槽满率超限、几何相交等工程错误必须继续阻断。下一阶段要解决的是“为什么通过前置检查后，进入 Task Worker 仍可能失败”的运行时一致性问题。
