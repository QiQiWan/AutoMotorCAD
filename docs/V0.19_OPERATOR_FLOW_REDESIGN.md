# MotorCAD Studio V0.19.0 — 操作员优先的流程与信息架构重构

## 1. 结论

V0.18.2 的底层工程对象已经较完整：Project、Design/Revision、Scenario/Revision、Task/Case、Result、Dataset，以及 Motor-CAD 运行门禁和问题诊断都已经存在。当前体验混乱的主要来源是这些工程对象被直接映射成大量并列页面，操作员需要自己判断“我现在应该去哪一页、当前对象属于哪个项目、设计修改应该在哪个页面完成、提交以后去哪里看”。

V0.19.0 将界面组织原则改为“按操作员完成工程工作的生命周期组织”，形成两个层级：

- 全局层：项目、运行环境、问题与日志、系统诊断。
- 项目层：概览、设计、仿真、结果、数据。

项目内部所有页面固定继承当前项目上下文。模板、任务记录、实时监控成为阶段内部的二级入口，不再与项目管理、系统配置并列。

## 2. 以操作员身份重新定义核心任务

操作员启动系统后，真正需要完成的连续任务通常只有以下链路：

1. 确认 Motor-CAD 能运行（首次配置或环境异常时）。
2. 选择或创建项目。
3. 创建 Design，并形成可追溯的 Design Revision。
4. 选择 Design Revision，设置工况和分析类型。
5. 先完成一条基准计算，确认模型、许可证、求解器和结果链路全部可用。
6. 基准通过后开展参数扫描、DOE 或优化。
7. 任务提交后连续进入实时监控。
8. 计算完成后审查工程结果。
9. 需要 AI/统计分析时，再将有效结果构建为数据集。
10. 发生异常时，从任务/Case 上下文进入问题诊断，并能够导出自包含诊断包。

这条链路应该成为界面骨架。Template、Worker、MessageLog、Automation Parameter、Data Factory 等都属于实现能力或阶段工具，不适合作为同一级导航目的地全部暴露给普通操作员。

## 3. V0.18.2 的结构性问题

### 3.1 顶层导航过载

V0.18.2 同时提供：启动配置、项目管理、项目驾驶舱、项目工作区、模板库、新建任务、实时监控、任务中心、结果查看器、数据工厂、日志与问题、系统诊断，共 12 个并列入口；顶部还存在一条“Motor-CAD → 项目 → 设计版本 → 资格检查 → 结果与数据”的流程条。

这形成了两套导航模型：

- 页面导航回答“系统有哪些页面”；
- 流程条回答“理论上应该按什么顺序做”。

操作员仍需自行把两套模型对应起来。

### 3.2 系统级状态与项目级工作混在一起

旧项目驾驶舱同时显示 CPU、内存、磁盘、Worker、模板资产和当前项目任务。操作员进入项目后，最关心的是工程状态、当前 Design、当前 Task、下一步动作。系统资源属于诊断维度，应放在系统诊断或运行环境中。

### 3.3 Design 定义与 Task 临时覆盖混合

旧任务创建页同时承担：

- 选择 Design Revision；
- 修改电机几何、绕组、运行参数；
- 修改材料和 Motor-CAD 高级参数；
- 设置 Scenario；
- 选择单次/扫描/DOE/NSGA-II；
- 选择输出；
- 预检查和提交。

这会让操作员难以判断当前修改属于“长期设计意图”还是“本次计算试算值”。任务能够保存成新 Revision，但入口仍然位于仿真页面，工程对象边界不清晰。

### 3.4 模板库被提升为长期工作区

模板的主要职责是创建 Design。创建完成后，操作员应回到 Design/Revision 上继续工作。模板长期占据顶级导航会让用户误以为后续每次计算都应重新选择模板。

### 3.5 仿真阶段被拆成三个平级页面

“新建任务 / 任务中心 / 实时监控”本质上是同一个仿真阶段的三个状态：配置、历史、执行。拆成顶级入口后，任务提交后的去向尤其容易产生断裂。

### 3.6 高级计算能力暴露过早

首次任务尚未跑通时，界面已经同时展示一维扫描、CSV、全因子、LHS、随机采样、Pareto、NSGA-II。用户很容易在基线模型尚未验证时直接进入大规模试验，导致大量失败任务和更复杂的诊断。

### 3.7 首屏目标不稳定

V0.18.2 即使已经完成 Motor-CAD 配置，启动后仍以运行环境为主要入口。对于每天使用的操作员，常规首要任务通常是继续项目，而不是重复确认安装路径。

## 4. V0.19.0 目标信息架构

```text
MotorCAD Studio
|
+-- 全局层
|   +-- 项目
|   +-- 运行环境
|   +-- 问题与日志
|   `-- 系统诊断
|
`-- 当前项目
    +-- 1 概览
    |   +-- 当前项目状态
    |   +-- 一个推荐下一步
    |   +-- 提交准备状态
    |   +-- Design / Scenario 摘要
    |   `-- 最近仿真
    |
    +-- 2 设计
    |   +-- Design / Revision
    |   `-- 从模板新建
    |
    +-- 3 仿真
    |   +-- 配置计算
    |   +-- 任务记录
    |   `-- 实时监控
    |
    +-- 4 结果
    |   +-- 单 Case 工程结果
    |   `-- 批量 / DOE / Pareto / 多 Case 对比
    |
    `-- 5 数据
        +-- 标准化与血缘
        `-- 数据集版本
```

这个结构把“系统管理”和“当前项目工作”分开，同时将项目内部的导航数量稳定在五个宏阶段。

## 5. 目标操作流程

### 5.1 首次使用

```text
启动
 -> 运行环境
 -> 绑定 Motor-CAD.exe
 -> 浅检查
 -> 深度检查
 -> 项目管理
```

### 5.2 日常返回用户

```text
启动
 -> 已检测到有效 Motor-CAD 运行环境
 -> 项目管理
 -> 进入项目
 -> 项目概览
 -> 根据“下一步”继续
```

### 5.3 设计流程

```text
项目概览
 -> 设计
 -> 无 Design：从模板创建
 -> Design Rev.1
 -> 修改设计参数
 -> 保存为 Rev.2 / Rev.3 ...
 -> 选择某个 Revision 用于仿真
```

长期几何、槽极、绕组等设计变更都在“设计”阶段形成新的不可变 Revision。

### 5.4 仿真流程

```text
仿真 / 配置计算
 -> 1 选择 Design Revision 基线
 -> 2 设置 Scenario / 边界条件
 -> 3 选择计算方式
 -> 4 选择输出
 -> 5 模型可解性检查 + 提交门禁
 -> 提交
 -> 自动进入实时监控
 -> 完成
 -> 结果
```

任务页面保留“高级：本次运行覆盖 Design Revision”折叠区，用于明确的临时试算；操作模式下弱化该能力。

### 5.5 基线优先规则

若当前项目没有成功的单次计算：

- 默认锁定扫描、DOE 和 NSGA-II 等批量模式；
- 显示“先跑通单次基准”的解释；
- 基准成功后自动开放高级计算方式。

这样可以把“模型可计算”与“设计空间探索”分成两个阶段，降低大批量失败任务的概率。

### 5.6 异常流程

```text
实时监控 / 任务记录
 -> Case 异常
 -> 根因诊断
 -> 参数 / 绕组 / 几何 / License / IPC / Timeout 分类
 -> 对应修复入口
 -> 重新建立任务
```

“问题与日志”保持全局能力，但工程用户应该优先从当前 Task/Case 的上下文看到最高优先级根因，再在需要时进入完整日志中心。

## 6. V0.18.2 与 V0.19.0 对比

| 维度 | V0.18.2 | V0.19.0 |
|---|---|---|
| 顶层导航 | 12 个并列页面 | 4 个全局入口 + 5 个项目阶段 |
| 项目进入页 | 直接进入项目工作区 | 先进入项目概览 |
| 项目切换 | 已取消右上角切换，但页面关系仍分散 | 项目 Shell 固定上下文，切换只回项目管理 |
| 运行环境 | 启动页始终强曝光 | 首次/异常时进入；配置正常后启动到项目管理 |
| 项目概览 | 混合系统资源、模板、任务 | 只保留项目状态、下一步、准备度、工程资产、最近任务 |
| 模板 | 独立顶级模块 | Design 阶段的“创建来源” |
| Design 修改 | 主要在任务页修改，可另存 Revision | Design 阶段直接编辑并创建新 Revision |
| Task 参数覆盖 | 与正式设计参数混合展示 | 收入“高级临时覆盖”折叠区 |
| 仿真入口 | 新建任务、任务中心、实时监控平级 | 仿真阶段下的三个二级入口 |
| Task 配置 | 一个长页面 | 五步向导 |
| DOE/优化 | 首次即可选择全部模式 | 操作模式先完成单次基准，再开放高级模式 |
| Task 提交后 | 跳转任务列表 | 自动进入该 Task 实时监控 |
| 流程提示 | 单独 Workflow Ribbon | 项目概览中的准备状态 + 单一推荐下一步 |
| 结果与数据 | 独立顶级页面 | 项目生命周期的第 4、5 阶段 |
| 复杂度模式 | Engineering 默认 | Operator 默认，工程/专家能力渐进披露 |

## 7. V0.19.0 已实现的界面迭代

### 7.1 全局与项目双层导航

顶部全局导航只保留“项目 / 运行环境 / 问题与日志 / 系统诊断”。进入项目后出现独立 Project Shell，展示当前项目和五个工程阶段。Design、仿真、结果和数据页面不提供项目下拉切换。

### 7.2 项目概览成为项目入口

进入项目后先展示：

- Design / Scenario / Task / Completed / Running / Failed 数量；
- 一个“推荐下一步”；
- 项目准备状态；
- Design/Scenario/Experiment 摘要；
- 最近仿真。

下一步由工程状态自动选择，例如“创建第一个 Design”“查看运行中的 Task”“检查 Motor-CAD”“完成资格检查”“先跑单次基准”“查看结果”。

### 7.3 项目阶段状态提示

项目导航会根据当前数据标记：

- Design 尚未创建：设计阶段为注意状态；
- 没有 Design：仿真阶段显示待准备；
- 没有完成任务：结果与数据阶段显示待准备；
- 有运行任务：仿真阶段显示运行状态。

阶段仍然允许查看，避免因过度硬锁导致用户无法检查空状态或历史信息。

### 7.4 Design Revision 正式成为设计修改中心

Design 页面增加“修改设计并创建新 Revision”。

- 从当前 Revision 读取参数；
- 按拓扑、主要几何、永磁体、绕组、运行参数等类别组织；
- 修改项实时高亮并统计；
- 保存后调用 Revision API 创建新的不可变版本；
- 历史 Task 继续指向旧 Revision。

### 7.5 Task Builder 五步化

原长页面在操作模式下重组为：

1. 基线
2. 工况
3. 计算方式
4. 输出
5. 检查提交

每一步只显示当前决策需要的内容。参数和材料临时覆盖收进基线步骤的高级折叠区。

### 7.6 提交后连续进入监控

Task 创建成功后直接选中该 Task 并进入实时监控，减少“提交成功 → 再去任务中心找刚才的任务 → 再打开监控”的重复操作。

### 7.7 项目管理显示 Motor-CAD 全局状态

项目管理页增加简化运行状态：未绑定、接口不可用、已绑定、深度检查通过。只有异常时需要回到运行环境处理。

## 8. 操作模式 / 工程模式 / 专家模式的职责

### Operator

适合常规仿真操作。强调推荐路径、基线优先、五步 Task Wizard，隐藏不必要的工程修改入口。

### Engineering

允许临时覆盖 Design Revision、保存工况、使用更完整的参数编辑和批量任务能力。

### Expert

开放 Motor-CAD Automation Parameter、Solver Controls、材料数据库细节。

### Developer

开放原生 AutomationName=Value、诊断和底层调试能力。

模式差异用于“渐进披露”，底层 Project/Design/Task 数据模型保持一致。

## 9. 后续建议：V0.20 优先级

V0.19.0 先完成信息架构重构。下一阶段建议按以下优先级继续：

### P0：上下文异常闭环

在实时监控和 Task 详情中加入固定“根因 / 建议操作 / 相关参数差异 / 打开日志”侧栏。让普通操作员多数情况下无需进入完整日志页。

### P0：Scenario 正式资产化

将 Scenario 作为“仿真 → 工况”子页管理，支持保存、复制、Revision、默认工况。Task Wizard 只负责选择 Scenario 或创建临时工况。

### P1：结果驱动的下一轮设计

结果页增加“基于此 Revision 创建下一设计版本”和“以此 Case 作为 DOE 基线”，形成 Result → Design / Simulation 的闭环。

### P1：Task 配方与复用

把 Analysis + Scenario + Requested Outputs + Quality Profile 保存为 Simulation Recipe，减少每天重复配置。

### P1：批量任务分层

把“一维扫描 / DOE / 优化”进一步分成“验证 → 探索 → 优化”三级模板，操作员选择工程目的，系统配置实验模式。

### P2：项目组合层

当项目数量增多后，再增加 Portfolio Dashboard，做跨项目进度、失败率、计算资源和数据资产统计。该能力保持在项目管理层，避免重新污染项目内部界面。

## 10. 验收标准

建议后续 UX 验收使用任务型指标：

1. 新用户从启动到提交首个基准 Task 的有效点击路径是否可稳定控制在一条主路径内。
2. 操作员在任何项目页面能否在 3 秒内回答“当前项目是什么、当前阶段是什么、下一步是什么”。
3. 创建 Design 后是否无需再次选择模板即可完成后续计算。
4. 修改几何/绕组时是否能明确知道会生成新的 Design Revision。
5. Task 提交后是否无需搜索即可看到该 Task 的实时状态。
6. 首次基准失败时是否能在 Task 上下文直接看到最高优先级根因。
7. 基准成功后是否能自然进入批量/DOE/优化流程。
8. 结果是否能明确追溯 Project → Design Revision → Scenario Revision → Task → Case → Dataset。

V0.19.0 已经实现 1–5 的主要结构，并继续复用 V0.18.2 的运行门禁、参数血缘和根因日志能力。第 6 项的“上下文异常闭环”和 Scenario 独立资产管理建议作为 V0.20 的首要工作。
