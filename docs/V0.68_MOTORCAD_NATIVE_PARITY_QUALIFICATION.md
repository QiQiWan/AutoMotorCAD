# MotorCAD Studio V0.68.0 — Motor-CAD Native Parity Qualification

## 1. Milestone objective

V0.68 closes the implementation side of the **Motor-CAD Native Parity Qualification** milestone for the target **Windows + Motor-CAD 2026R1** workstation. The qualification contract covers four representative machine profiles:

| Profile | Studio template | Native family represented | Main parity focus |
|---|---|---|---|
| BPM | `a1` | Brushless PM generic family baseline | common BPM geometry / winding / materials / EMag contract |
| SPM | `i5_Industrial_SPM_Servo_Tooth_Wound` | industrial surface-PM servo | concentrated winding, SPM magnet geometry, common material chain |
| IPM | `e9_eMobility_IPM` | eMobility interior-PM | embedded magnet geometry, 48-slot/8-pole winding, high-current EMag |
| AFPM | `e14_eMobility_AFM` | e14 axial-flux/YASA-style family | axial geometry and double-rotor material/parameter/result chain |

BPM is treated as the Motor-CAD brushless-PM family baseline; SPM and IPM remain topology-specific parity profiles. This avoids certifying the generic family only through one SPM-specific model.

The target acceptance chain is:

```text
Studio MTT / canonical registry
        ↓
registered Motor-CAD 2026R1 template or verified local MOT
        ↓
canonical readback
        ↓
Studio write → native readback round trip
        ↓
Motor-CAD geometry + winding validation
        ↓
component material write/readback
        ↓
native Radial/Axial geometry evidence
        ↓
real EMag calculation
        ↓
Studio extraction ↔ native direct readback
        ↓
Motor-CAD CSV + MOT + screenshots + structured evidence
        ↓
verified local MOT promotion only after all required automatic checks pass
```

## 2. Important qualification boundary

The current build environment is Linux and has no licensed Motor-CAD 2026R1 GUI/RPC installation. Therefore this release does **not** claim that BPM/SPM/IPM/AFPM have already passed a real Windows Motor-CAD run.

Two completion numbers are deliberately separated:

- **Studio V0.68 implementation completion:** 100% for the qualification harness, APIs, UI, evidence model, process isolation and automated contracts.
- **Native workstation qualification:** 0% in the packaged release until the suite is executed successfully on the target Windows + Motor-CAD 2026R1 workstation.

A PASS generated by Linux unit tests cannot change native qualification state. Only records in `native_parity_runs` for the configured Motor-CAD version count toward the workstation matrix.

## 3. Qualification environment is version-frozen

V0.68 freezes the external qualification environment to:

- Motor-CAD target: `2026R1`
- PyMotorCAD: `ansys-motorcad-core==0.8.8`
- Studio database schema: `22`
- Native parity contract version: `1`

The Windows launcher checks the PyMotorCAD version before starting the suite and installs the pinned `requirements-motorcad.txt` environment if required. The worker also records and checks the runtime PyMotorCAD version. A version mismatch remains visible in the evidence and blocks qualification while allowing further diagnostics to be collected.

This prevents a workstation silently changing its automation API surface during a qualification campaign.

## 4. Native parity profile contract

The profile configuration is in `config/native_parity_profiles.yaml`.

Each profile declares:

- required geometry parameters;
- required winding parameters;
- required operating inputs;
- required component materials;
- required scalar and series results;
- native Geometry screens that must be captured;
- strict parameter/result tolerances.

Current plan size:

| Profile | Geometry | Winding | Materials | Inputs | Results |
|---|---:|---:|---:|---:|---:|
| BPM | 8 | 3 | 4 | 4 | 6 |
| SPM | 16 | 3 | 5 | 5 | 7 |
| IPM | 15 | 3 | 5 | 5 | 7 |
| AFPM | 15 | 3 | 6 | 5 | 7 |

The normal successful profile run contains 18 required high-level checks, with row-level comparisons inside parameter, winding, material and result checks.

## 5. Model baseline policy

### 5.1 Validation/production remains strict

Normal `validation` and `production` execution policies still require a verified local `.mot` baseline. Missing verified MOT files are rejected.

### 5.2 V0.68 native qualification may bootstrap a candidate

`model_policy="native_parity"` can load the target-version registered Motor-CAD template when a verified local MOT does not yet exist. The registered model is treated only as a candidate baseline.

The worker saves `native_baseline.mot` immediately for evidence, but promotes it to the configured `data/verified_models/<template>/template.mot` path only when all prior required parity checks pass. A failed parity run cannot overwrite or create a production/validation baseline.

This closes a bootstrapping problem in previous releases: the project required verified local MOTs for strict validation but had no target-workstation procedure that could safely create the first verified baseline.

## 6. Geometry parity

Geometry is checked at four levels.

### 6.1 MTT → canonical defaults

Studio reads the source `.mtt` and resolves the current canonical defaults. During V0.68 audit a concrete parser gap was found and fixed: `Slot_Opening` existed in the Motor-CAD templates but was absent from the canonical MTT source map.

After repair the baseline values are:

- `a1`: slot opening `4 mm`
- `i5`: slot opening `2 mm`
- `e9`: slot opening `3 mm`
- `e14`: slot opening `3 mm`

This was an actual Studio/native geometry parity defect rather than a presentation-only issue.

### 6.2 Native readback

All required canonical geometry parameters are read from the loaded Motor-CAD model through the registry mapping and compared against Studio defaults with strict absolute/relative tolerances.

### 6.3 Studio write → native readback

Read-only equality can hide a broken write mapping. V0.68 therefore writes the same canonical values back through Studio's normal automation mapper and reads them again from Motor-CAD. No intentional geometry perturbation is introduced; the operation is idempotent. Missing automation mappings, write failures and post-write changes are blocking differences.

### 6.4 Motor-CAD native geometry authority

The worker runs the native geometry validation path after the write round trip. Explicit canonical geometry values that Motor-CAD silently adjusts are treated as qualification problems rather than accepted as harmless defaults.

`studio_geometry_contract.json` records the topology, Studio value, native value, unit and actual Motor-CAD variable for every required geometry field.

## 7. Native visual evidence

For every configured profile the qualification worker makes the Motor-CAD UI visible, initializes tab names, navigates explicitly to each Geometry screen, and captures both required views:

- `Geometry;Radial`
- `Geometry;Axial`

All configured screenshots are mandatory automatic evidence. A single successful screenshot is no longer sufficient.

Motor-CAD automation intentionally does not repaint every visible control after each script assignment, so the worker explicitly displays the relevant geometry screen immediately before capture.

The run also writes `native_visual_review_manifest.json`. It links the native screenshots to `studio_geometry_contract.json` and gives a short operator checklist for final visual sign-off. The operator review is kept explicit because Studio uses an interactive engineering schematic for some regions while Motor-CAD native geometry is the final geometric authority.

## 8. Winding parity

V0.68 checks both Motor-CAD's native winding diagnostic and the structured winding topology.

The structured path uses `get_winding_coil(phase, path, coil)` and verifies:

- a structured native coil list is returned;
- expected phase coverage is present;
- expected parallel-path coverage is present;
- go/return slots stay inside the expected slot domain, accepting the native one-based or zero-based indexing convention;
- every native coil has the expected `turns_per_coil`.

The native winding pattern and structured winding definition artifacts are retained in the evidence package.

This check is important for cases where the Studio winding visualization can look plausible while the actual phase/path/slot topology sent to Motor-CAD differs.

## 9. Material parity

For every required component the worker performs two checks:

1. Studio material assignment → Motor-CAD component material write/readback.
2. Independent native component material snapshot compared with the template's frozen default assignment.

This qualification reuses the material provenance system introduced earlier, while V0.68 focuses on component assignment parity. It does not modify the source Motor-CAD material database during qualification.

## 10. Operating-input parity

The required operating inputs are included in the same canonical write/readback contract as geometry and winding settings. Current profiles cover the relevant subset of:

- shaft speed;
- peak current;
- RMS current where applicable;
- DC bus voltage;
- phase advance.

The exact Motor-CAD automation variable selected by the registry is stored in each row of the evidence.

## 11. Solver and result parity

After model, geometry, winding, material and input checks, the worker obtains the EMag licence and executes a real `do_magnetic_calculation()`.

Required outputs are separated into scalar and series contracts. Studio extracts each result through its production result registry. The worker then independently reads the same selected Motor-CAD variable/graph again in the same native session and performs strict equality/tolerance comparison.

Typical required results include:

- shaft torque;
- peak line voltage;
- efficiency;
- total loss;
- magnet loss;
- torque-angle curve;
- air-gap flux-density curve for the SPM/IPM/AFPM profiles.

The native Motor-CAD EMag solution is additionally exported to CSV. This produces evidence that can be reviewed independently of Studio's result viewer.

## 12. Evidence and database model

Database Schema 22 adds `native_parity_runs`.

A parity record is scoped by:

- profile;
- template;
- Motor-CAD target version;
- status / qualification state;
- full JSON evidence;
- artifact directory;
- creation time.

The qualification matrix only queries evidence for the active Motor-CAD version. A PASS from an older Motor-CAD release cannot qualify 2026R1.

Each evidence package can include:

- `native_baseline.mot`;
- `studio_geometry_contract.json`;
- `native_visual_review_manifest.json`;
- radial/axial native PNGs;
- winding pattern/definition evidence;
- parameter write/readback audit;
- material write/readback audit;
- Motor-CAD EMag CSV;
- `native_parity_evidence.json`;
- `native_parity_report.md`;
- verified MOT promoted on a full pass.

The API also exposes an artifact ZIP for each recorded run.

## 13. Process isolation

`motorcad_studio/runtime/native_parity_process.py` runs each profile in a separate child process. A stalled Motor-CAD RPC/GUI/licence interaction can therefore be terminated as a process tree without taking down the FastAPI/Studio host.

The suite executes BPM, SPM, IPM and AFPM sequentially by default. `--stop-on-failure` is available for diagnostic runs.

## 15. Windows execution procedure

On the target workstation:

1. Install/register Motor-CAD 2026R1 for automation and verify the correct version starts.
2. Close unrelated Motor-CAD instances before the baseline qualification campaign.
3. Extract the V0.68 package to a local writable directory.
4. Start from a Python environment used by Studio.
5. Double-click `run_v068_native_parity_windows.bat`, or run the Python suite directly.
6. Do not edit models manually while the suite owns the Motor-CAD instance.
7. Inspect `data/runtime/native_parity/suites/<suite-id>/suite_report.md` after completion.
8. For any failed profile, inspect the profile `native_parity_report.md`, mismatch rows, native screenshots and Motor-CAD message evidence before modifying a mapping or renderer.
9. Run the full suite again after each correction. A profile is considered automatic `NATIVE_QUALIFIED` only when all required automatic checks pass.
10. Complete the visual-review checklist using the native screenshots and Studio geometry contract before final engineering sign-off.

Planning only, without launching Motor-CAD:

```bat
python scripts\run_v068_native_parity.py --plan
```

Full suite:

```bat
python scripts\run_v068_native_parity.py --profiles bpm,spm,ipm,afpm --timeout 1200
```

## 17. Remaining native acceptance work

The following items require the target Windows workstation and remain intentionally unclaimed in this package:

- actual Motor-CAD 2026R1 process launch and licence acquisition;
- actual registered-template readback for BPM/SPM/IPM/AFPM;
- native winding API behavior on each target model;
- native component-material aliases on the installed database/version;
- real EMag solve convergence for each baseline;
- native result variable/graph resolution against the installed version;
- Radial/Axial screenshot contents;
- creation/promotion of the four verified local MOT baselines;
- Windows DPI/GUI behavior during native screenshot capture;
- operator visual sign-off of Studio schematic versus native geometry.

Consequently, `RELEASE_MANIFEST.json` records **native workstation qualification = 0%** for the packaged Linux build. The percentage becomes evidence-driven only after the target workstation records PASS runs for all four profiles.

## 18. Release decision

V0.68 is ready to move from implementation to the target-workstation qualification campaign. The code path, evidence contract and correction loop are complete enough that any remaining difference should now appear as a named parameter/winding/material/result/screenshot blocker rather than as an ambiguous “Studio and Motor-CAD look different” problem.

V0.69 should begin only after the four-profile 2026R1 matrix is complete and the visual-review checklist has been signed off. At that point the next milestone can concentrate on Results & Optimization Workbench convergence without carrying unresolved native model ambiguity forward.
