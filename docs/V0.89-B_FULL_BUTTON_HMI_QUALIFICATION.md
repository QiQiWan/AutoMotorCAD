# V0.89-B — Full Button HMI Qualification

Release: **MotorCAD Studio 0.89.2 / Schema 45**

## Purpose

V0.89-B turns the browser control surface into an auditable qualification surface. Every rendered button receives a semantic action identity, a stable control identity and handler-ownership evidence. Fixed controls are additionally exercised by an actual-click full-shell browser sweep.

## Authority

- Authority: `HMIActionQualificationAuthorityV1`
- Contract: `0.89-B`
- Runtime module: `motorcad_studio/static/hmi/action-registry.js`
- Developer panel: System -> HMI interaction qualification

## Registration model

Each button is annotated with:

- `data-hmi-origin`: `fixed` or `dynamic`
- `data-hmi-action-id`: semantic action
- `data-hmi-control-id`: stable control identity
- `data-hmi-family`: action family

Handler qualification accepts four explicit ownership modes:

1. direct `addEventListener('click', ...)` registration;
2. inline `onclick`;
3. declared delegated action family;
4. declared deferred page owner for controls whose module binds after its page mounts.

A MutationObserver continuously qualifies dynamically created buttons. Dynamic-family counts use unique control identities so repeated scans do not inflate evidence.

## Qualification dimensions

For every currently rendered control the registry records:

- stable identity;
- action/family identity;
- origin and UI scope;
- visible/enabled state;
- destructive-action flag;
- handler evidence and direct-handler count;
- qualification status.

The developer panel can execute qualification and export the current JSON evidence.

## Fixed-control browser sweep

The V0.89-B full-shell test loads the complete production `index.html`, inlines the production scripts, supplies an isolated API sandbox, and then walks every fixed button.

Current 0.89.2 result:

- fixed controls: **87**;
- stable identity + handler qualification: **87/87 (100%)**;
- actual click sweep: **83 triggered**;
- correctly workflow-gated at the sweep point: **4**;
- missing controls: **0**;
- uncaught browser page errors: **0**;
- console errors: **0**.

The four gated controls are the Design/Analysis/Result project-stage navigation buttons before an active project has made those stages reachable, plus Case comparison before Case selection. Their disabled state is therefore expected evidence.

See `docs/V0.89-B_HMI_QUALIFICATION_MATRIX.md` for the fixed-control matrix.

## Dynamic controls

Dynamic controls are state-dependent and cannot be represented by one frozen instance count. The registry therefore qualifies all currently rendered dynamic buttons and records observed semantic families. The same handler/identity criteria apply when they appear.

At initial full-shell bootstrap the current harness observes five dynamic controls; the combined rendered surface qualifies at 100%. Subsequent project/task/result states are observed through the same mutation-based registry.

## Release-gate hardening

The current release gate includes V0.89-A and V0.89-B dedicated tests. Test files execute in separate interpreter processes via `scripts/run_pytest_file_isolated.py` after pytest teardown. This prevents third-party interpreter-exit hooks from stalling the next qualification file after test results have already completed.

## What this evidence proves

The local browser evidence proves that the complete production shell can bind and exercise its fixed control surface without uncaught JavaScript errors under an isolated deterministic API sandbox, and that rendered dynamic controls are registered by the same authority.

It does not prove that every control has completed a licensed Motor-CAD operation on Windows. Native Motor-CAD workstation qualification remains a separate production gate.
