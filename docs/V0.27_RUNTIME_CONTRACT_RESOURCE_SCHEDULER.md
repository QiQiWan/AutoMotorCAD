# V0.27 Runtime Contract + Atomic Resource Scheduler

## 1. 本轮优化目标

V0.26 已经解决正式 Case 内部的 Validate-and-Run 分离：参数回读、Motor-CAD 原生 Geometry/Winding 检查和 Full Solve 可以在同一个 Persistent Worker、同一个 Motor-CAD Session 中连续完成。继续审查运行链后仍有四类高风险问题：

1. Worker、Studio 本地许可证容量、内存余量分别控制时，Case 可能先占有一种稀缺资源，再等待另一种资源；
2. UI 中手动绑定的 `Motor-CAD.exe` 与进程启动时冻结的 `settings.motorcad_exe` 可能分离，导致“界面显示绑定成功，但 Task / Preflight / Worker 仍使用旧启动路径”；
3. Persistent Worker 已经可以复用，但缺少面向真实 Windows 工作站的长期稳定性证据，无法回答“这个环境连续复用多少 Case 后仍可靠”；
4. 监控中的内存阈值使用变化消息作为告警签名，82.1%、82.2%、82.3% 可能被识别成不同告警，形成大量 ALERT / RESOLVED 抖动。

V0.27 因此把运行时定义为三层权威：

```text
Studio admission contract
  Worker token + declared licence capacity + memory headroom
                    ↓
Motor-CAD native runtime authority
  get_licence() + actual RPC / model / solver behaviour
                    ↓
Runtime Contract evidence
  observed Case success/failure + Worker generation + RSS + environment signature
```

Studio 的本地许可证容量只负责限制自身并发，不能代表浮动许可证服务器的实时库存。真正的上下文许可证仍在 Solver 内通过 PyMotorCAD / Motor-CAD 原生接口获取。

## 2. 关键问题：手动绑定路径此前并非真正的全局运行时权威

### 2.1 旧链路

安装管理器会把用户手工选择结果保存到：

```text
data/runtime/motorcad_installation.json
```

页面随后显示该路径已经成为选中安装，并调用 PyMotorCAD `set_motorcad_exe()`。

但 `Settings` 在进程启动时已经冻结：

```text
settings.motorcad_exe
```

旧代码中仍有 Task payload、Preflight、Qualification 或 Worker base payload 从这个启动值获取路径。因此可能形成：

```text
UI selected exe
I:\ANSYS Inc\v261\motorcad\MotorCAD.exe

                    ≠

Task/Worker startup exe
<MOTORCAD_STUDIO_MOTORCAD_EXE at application start>
```

这类问题非常危险，因为 UI 与日志表层都可能显示“路径已绑定”，实际求解行为却依赖另一个安装或 Windows Automation 注册版本。

### 2.2 V0.27 修复

现在运行期统一使用：

```text
TaskManager.motorcad_exe
```

作为“当前有效执行路径”。

启动时：

```text
persisted selected installation
        ↓ exists?
       yes
        ↓
TaskManager.update_motorcad_exe(...)
```

运行期重新选择安装时：

```text
InstallationManager.select()
        ↓
configure_pymotorcad()
        ↓
TaskManager.update_motorcad_exe()
        ↓
Persistent Worker base_payload 更新
        ↓
旧 Worker recycle
        ↓
Runtime Contract environment rotate
```

以下路径都改为读取有效执行路径：

- Task 正式执行；
- Persistent Worker；
- Motor-CAD Adapter；
- deep preflight；
- runtime geometry validation；
- `scripts/check_motorcad.py`；
- `scripts/verify_motorcad_runtime.py`；
- `scripts/bootstrap_motorcad.py`；
- Windows runtime contract campaign。

诊断包同时保存：

```text
motorcad_exe_config       # 环境变量/启动配置
motorcad_exe_effective    # 当前真正执行路径
```

两者不同并不再被隐藏。

## 3. Atomic Runtime Resource Scheduler

新增：

```text
motorcad_studio/runtime/resource_scheduler.py
```

### 3.1 为什么需要原子资源分配

V0.26 以前可以形成：

```text
Case A
  ↓
获得 EMAG 本地许可槽
  ↓
等待 Worker 10 min
```

此时这个许可槽虽然没有真正开始 Motor-CAD Case，却已经被 Studio 的调度层占用。

V0.27 统一申请：

```text
Case Request
   │
   ├─ Worker token
   ├─ Analysis → local licence capacity
   └─ memory reservation
           ↓
全部满足
           ↓
Runtime Resource Lease
```

如果任一条件不足，Case 保持在队列，不占有其他资源。

### 3.2 Analysis → 本地许可容量

当前默认映射：

```text
emag                       → EMAG
thermal_steady             → THERMAL
thermal_transient          → THERMAL
emag_thermal               → EMAG + THERMAL
emag_thermal_coupled       → EMAG + THERMAL
mechanical                 → MECHANICAL
lab_magnetic               → LAB
lab_operating_point        → LAB
```

有效并发等于 Worker 容量和相关本地许可容量的最小值。

例如：

```text
Worker = 3
EMAG   = 2
THERM  = 1

emag effective concurrency          = 2
thermal_steady effective concurrency = 1
emag_thermal effective concurrency   = 1
```

### 3.3 Runtime Resource Lease

新 Case 会保存：

```text
runtime_resource_lease_id
resource_wait_ms
```

并将完整 Lease 传入 `execution_lease.json`：

```json
{
  "lease_id": "RRL-...",
  "task_id": "TASK-...",
  "case_id": "TASK-...-C0001",
  "analysis": "emag_thermal",
  "licenses": ["EMAG", "THERMAL"],
  "memory_reservation_mb": 1024,
  "wait_ms": 238.4
}
```

Case 日志增加：

```text
WAITING_FOR_RUNTIME_RESOURCES
RUNTIME_RESOURCE_LEASE_ACQUIRED
```

资源超时与配置不可能满足也分开处理：

```text
RESOURCE_TIMEOUT
RESOURCE_UNAVAILABLE
```

### 3.4 内存 Admission

配置项：

```text
MOTORCAD_STUDIO_RUNTIME_MIN_FREE_MEMORY_MB
MOTORCAD_STUDIO_RUNTIME_CASE_MEMORY_MB
```

默认：

```text
minimum free headroom = 1536 MB
per-Case reservation  = 1024 MB
```

这是一层保守的 admission guard。Runtime Contract 会持续记录真实 Motor-CAD RSS 高水位并给出 `observed max * 1.2` 的推荐值。当前版本不会自动改写用户配置，以避免少量样本导致运行策略漂移。

## 4. Native Licence 仍然是最终权威

Atomic Scheduler 的许可证数量来自 Studio 本地配置：

```text
MOTORCAD_STUDIO_LICENSE_EMAG
MOTORCAD_STUDIO_LICENSE_THERMAL
MOTORCAD_STUDIO_LICENSE_MECHANICAL
MOTORCAD_STUDIO_LICENSE_LAB
```

这些值用于回答：

> Studio 自己最多允许同时启动多少个对应分析 Case？

它们不能回答：

> 此刻浮动许可证服务器还剩多少真实 licence？

真实 Case 中仍执行：

```text
show context
↓
MotorCAD.get_licence()
↓
成功后才 do_*_calculation()
```

因此外部 Motor-CAD 用户在 Studio admission 之后抢占了浮动许可证时，真实 native checkout 仍可能失败。这种情况应该被记录成真实许可证失败，后续版本可以基于失败构建 cooldown / circuit breaker；不能用 Studio 本地计数虚构许可证服务器状态。

## 5. Persistent Worker Capability Handshake

V0.27 的 Python Worker 启动后先报告能力，不主动创建 Motor-CAD 实例：

```text
Worker MCW-01 G2
├─ Python version / architecture / platform
├─ PyMotorCAD available
├─ PyMotorCAD version
├─ target Motor-CAD version
├─ selected Motor-CAD version
├─ effective Motor-CAD.exe
├─ executable exists
├─ executable fingerprint
├─ installation ID
├─ blackbox flag
└─ compatible / reason
```

真实 Case 分配使用：

```text
require_compatible=True
```

不兼容 Worker 不接收真实 Motor-CAD Case。

新增 API：

```text
POST /api/runtime/motorcad-worker-pool/probe
```

这个能力探测只启动/检查 Python owner 和 PyMotorCAD import contract，设计上不主动 launch Motor-CAD，也不进行 licence checkout。

## 6. Runtime Contract：把“感觉稳定”变成运行证据

新增：

```text
data/runtime/runtime_contract.json
```

记录真实 Case：

```text
analysis
success / failure
Worker ID
Worker generation
execution lease
runtime resource lease
native licence evidence
Worker RSS
last failure
success streak
```

### 6.1 Observational 状态

```text
UNVERIFIED
  没有 V0.27 真实 Case

EARLY_EVIDENCE
  有少量成功样本

WARMING
  当前 Worker generation 连续成功 >= 5

STABLE_OBSERVED
  连续成功 >= 20

ENDURANCE_OBSERVED
  连续成功 >= 100 且观察记录无失败
```

这些状态只代表 Studio 对当前工作站环境的观测，并不代表 Ansys 认证。

### 6.2 Environment Signature

Runtime Contract 绑定：

```text
target Motor-CAD version
effective Motor-CAD.exe
machine
platform
Python version
```

安装路径或环境发生变化时：

```text
old evidence
  ↓
environment_history

new environment
  ↓
UNVERIFIED / new evidence
```

因此不会把某个旧 Motor-CAD 安装下的 100 次连续成功直接沿用到新安装。

### 6.3 Staleness

默认超过 168 h 没有新的真实 Case，会把 evidence 标记为 stale。

配置：

```text
MOTORCAD_STUDIO_RUNTIME_CONTRACT_STALE_HOURS
```

## 7. Windows Runtime Contract Campaign

新增：

```text
scripts/run_motorcad_runtime_contract.py
```

用于目标 Windows 工作站显式验证真实复用。

示例：

```bat
python scripts\run_motorcad_runtime_contract.py ^
  --cycles 20 ^
  --confirm-license-use
```

100 次长期验证：

```bat
python scripts\run_motorcad_runtime_contract.py ^
  --cycles 100 ^
  --confirm-license-use
```

需要执行求解时：

```bat
python scripts\run_motorcad_runtime_contract.py ^
  --cycles 100 ^
  --analysis emag ^
  --registered-template i5 ^
  --solve ^
  --confirm-license-use
```

工具显式要求：

```text
--confirm-license-use
```

原因是 `get_licence()` 会进入真实 Motor-CAD 许可证流程。

每个循环执行：

```text
MotorCAD(...reuse...)
↓
MessageDisplayState = 2
↓
Scripting screen (best effort)
↓
clear_message_log()
↓
optional canonical template load
↓
get_licence()
↓
optional solve
↓
get_messages()
↓
RSS evidence
↓
set_free()
```

最后一轮退出实例。

可选：

```text
--studio-url http://127.0.0.1:8765
```

把正式 report 回传到：

```text
POST /api/runtime/contract/formal
```

## 8. Runtime Alert 去抖与迟滞

历史日志中内存使用率在 82% 左右波动时，旧告警签名包含完整 message：

```text
MEMORY_HIGH 82.1%
MEMORY_HIGH 82.2%
MEMORY_HIGH 82.3%
```

因此可能被当成三个不同 alert。

V0.27 使用稳定身份：

```text
alert identity = code + entity
```

并加入 hysteresis：

```text
Disk high       enter >= 80%, clear < 76%
Memory high     enter >= 82%, clear < 78%
Memory critical enter >= 92%, clear < 89%
```

这样监控更接近状态机，而不是阈值附近每次采样都重新生成问题。

Runtime Scheduler 队列等待超过 5 s 时也会生成可解释的：

```text
RUNTIME_RESOURCE_QUEUE
```

并附：

```text
WORKER_CAPACITY
LICENSE_EMAG_BUSY
LICENSE_THERMAL_BUSY
MEMORY_ADMISSION
...
```

## 14. 尚未宣称解决的问题

V0.27 没有把以下事项包装成已完成：

1. 本地声明的 licence capacity 不能精确预测浮动许可证服务器实时库存；
2. 严格 FIFO 资源队列在复合分析请求位于队首时仍可能出现 Head-of-Line Blocking；
3. Case memory reservation 当前是保守静态值，虽然 Runtime Contract 已经能给出观测推荐；
4. 持久 Worker 的 100 / 500 Case 长时间可靠性必须由 Windows Contract Test 确认；
5. 数据库仍是 `CREATE TABLE IF NOT EXISTS + _ensure_column` 迁移体系；
6. 浏览器 Playwright E2E 与 Motor-CAD fault injection 仍需建设。

这些问题构成 V0.28 的主要工作。
