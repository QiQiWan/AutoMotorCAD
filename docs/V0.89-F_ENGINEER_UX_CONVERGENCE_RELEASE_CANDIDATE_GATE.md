# V0.89-F — Engineer UX Convergence & Release Candidate Gate

Release target: **MotorCAD Studio 0.89.6 / Schema 45**  
Authorities: **EngineerUXConvergenceV1** + **ReleaseCandidateGateV1**

## 1. Objective

V0.89-F is the convergence iteration for the V0.89 line. It does not add a new Motor-CAD modelling or solver authority. It turns the existing Project → Solution → Motor Revision → Analysis → Task → Result lineage and the V0.89-A–E qualification chain into one engineer-facing release candidate surface.

The default Guided view must answer four questions continuously:

1. **当前位置** — which engineering step and object the user is operating;
2. **当前状态** — ready, calculating, blocked, failed, or requiring validation;
3. **需要处理** — the highest-priority blocker in engineer language;
4. **下一步** — one concrete next action that follows the authoritative workflow.

Technical hashes, authority names, raw evidence objects and runtime internals remain available in Expert/Developer surfaces.

## 2. Engineer UX convergence

### 2.1 Persistent engineer focus bar

`EngineerUXConvergenceV1` renders one persistent four-cell strip under the project shell. It consumes `MCSEngineeringContextV3` and `GlobalWorkflowTruthV1`; it does not create an independent workflow state.

The focus bar derives its information from the same authoritative context used by routing and release gates. The optional **执行下一步** action routes through the normal navigation authority, so it cannot bypass V0.89-C dirty-editor preparation/commit/rollback rules.

In Guided/operator mode, the older technical lineage breadcrumb is hidden to reduce duplicate state presentation. Expert/Developer modes retain the technical breadcrumb and all low-level evidence panels.

Expert/Developer evidence surfaces keep the original authority vocabulary where it is needed for diagnosis and traceability. The terminology layer changes rendered text only; IDs, hashes, lineage, API payloads and persisted schema remain unchanged.

### 2.3 Core interaction rule

The default engineer flow remains **Design → Validate → Decide**. A user should be able to complete the common path without understanding Python, JSON, worker leases, BindingPlan hashes, ResultBundle schemas or authority implementation names. Advanced evidence remains one drill-down away rather than being removed.

## 3. Release Candidate Gate

`ReleaseCandidateGateV1` consolidates release status into two intentionally different conclusions:

- **LOCAL_RC_READY_WORKSTATION_PENDING** — all distributable code/static/HMI regression gates are green, but target-workstation evidence is still missing;
- **FORMAL_RC_READY** — local automated gates, licensed Windows/Motor-CAD evidence, live Golden Journeys, both soak layers and human engineer acceptance are all green;
- **RC_BLOCKED** — one or more automated release checks are not green.

A build under active regression uses `release_state=BUILD_IN_PROGRESS`. It cannot report Local RC Ready. The release manifest is switched to `FINALIZED` only after the final inventory, HMI sweep, clean-source check and package hash are frozen.

### 3.1 Automated RC checks

The automated gate verifies at least:

- release manifest version equals the package version;
- `EngineerUXConvergenceV1` and `ReleaseCandidateGateV1` are present in the manifest;
- the manifest is `FINALIZED`;
- V0.89-F release-gate regression is recorded PASS;
- full test inventory, Python compile and JavaScript syntax are PASS;
- Browser HMI regression is PASS;
- fixed-control HMI registration is 100%;
- fixed-button actual-click sweep has zero missing controls, page errors and console errors;
- JS/CSS assets are loaded once, exist on disk and use the exact current version pin;
- the engineer focus bar is present exactly once;
- V0.89-A Global Workflow Truth and V0.89-C Navigation Transaction gates remain PASS.

### 3.2 Formal RC predecessor chain

Formal RC requires all six checks:

1. automated Release Candidate Gate;
2. formal licensed Windows + Motor-CAD 2026R1 Native qualification;
3. V0.89-D SPM/IPM/AFPM live UI Golden Journeys;
4. formal Native 100/500 Case Production Soak;
5. V0.89-E UI 100/500 + 12/12 recovery/fault qualification;
6. V0.89-F 12/12 evidenced engineer human acceptance.

A local unit/E2E run can satisfy item 1 only. It cannot promote items 2–6.

## 4. Engineer human acceptance

The formal checklist has 12 fixed items:

1. PROJECT_ENTRY_CLARITY
2. STARTER_TO_DESIGN_CLARITY
3. EDITOR_SAVE_CANCEL_BACK
4. VALIDATION_GATE_CLARITY
5. SOLVE_PROGRESS_VISIBILITY
6. RESULT_DECISION_CLARITY
7. RECOVERY_MESSAGE_CLARITY
8. GUIDED_TERMINOLOGY_CLARITY
9. VISUAL_CONTRAST_LAYOUT
10. NO_DEAD_END_NAVIGATION
11. CONTEXT_ALWAYS_VISIBLE
12. CLEAN_RELAUNCH

The shipped template starts with every item **PENDING** and overall status **FAIL**. Formal import is accepted only when:

- the platform starts with Windows;
- the Studio version exactly matches the running build;
- all 12 required IDs are present;
- all 12 statuses are PASS;
- all 12 items carry a non-empty evidence reference;
- the overall status is PASS;
- a reviewer identity is supplied.

This prevents the package from shipping a pre-approved human checklist.

The template is `motorcad_studio/acceptance/rc_human_acceptance_checklist.json`.

## 5. Windows execution

The integrated production runner now creates a `V089F-*` top-level evidence root and retains the predecessor chain underneath it:

`V0.88-F Native → V0.89-D Golden Journey → Native 100/500 Soak → V0.89-E UI Resilience → V0.89-F RC Gate`

Run the automated workstation chain:

```powershell
.\run_windows_production_qualification.ps1 -Install
```

Without a completed human checklist, the runner freezes the automated/local RC evidence and exits fail-closed for formal RC. Complete the shipped checklist using evidence from the workstation walkthrough and rerun:

```powershell
.\run_windows_production_qualification.ps1 -Install -HumanAcceptanceJson .\rc_human_acceptance_completed.json
```

The final V0.89-F evaluator is also available directly:

```powershell
python scripts\evaluate_release_candidate.py --human-acceptance .\rc_human_acceptance_completed.json --require-formal
```

## 7. Qualification boundary

The development environment used to build this package is not a licensed Windows + Motor-CAD 2026R1 workstation. Therefore the package can close the distributable code/HMI RC gate, but formal workstation evidence remains **PENDING** until the integrated Windows runner and the 12-item engineer acceptance are executed on the target workstation.

No local unit test, component browser test or Linux-hosted diagnostic is promoted to formal Motor-CAD workstation evidence.
