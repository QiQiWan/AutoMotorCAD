# V0.15 Implementation — Geometry Guard, Session Diagnostics and Engineering Compare

## 1. Motivation

V0.14 solved the highest-risk geometry bug exposed by a real e14 run: untouched MTT candidate defaults were being rewritten into the active Motor-CAD model, and Motor-CAD rejected the resulting Slot Opening / StatorAir geometry. V0.15 addresses the next layer: detect obvious geometry conflicts before launching Motor-CAD, make historical logs distinguishable from current failures, and make optimization candidates easier to compare.

## 2. Geometry safety pipeline

The geometry pipeline is now layered:

```text
Parameter edit
  -> Studio local geometry guard
  -> optional Motor-CAD geometry check
  -> Task validation
  -> Case execution-boundary geometry guard
  -> isolated Motor-CAD worker
  -> Motor-CAD geometry validation / safe recovery
  -> solve
```

`geometry_guard.py` intentionally contains only relations that are safe to infer from canonical engineering parameters. It does not attempt to reconstruct all Motor-CAD geometry constraints.

The guard calculates topology-aware engineering quantities including reference diameter, approximate slot pitch, slot-opening ratio and tooth-width ratio. A violation involving an explicit design variable can block execution. A suspicious value that only came from a candidate template default becomes a Warning, because Motor-CAD runtime defaults remain authoritative for untouched parameters.

## 3. Real geometry pre-check

`POST /api/templates/{template_id}/geometry-check` runs the existing qualification runner in an isolated process. It passes only `explicit_parameter_ids`, so clicking the check button cannot accidentally rewrite all UI/template defaults.

The returned payload contains parameter roundtrip information and actual Motor-CAD geometry status. This lets the user separate:

- Studio heuristic risk;
- Motor-CAD actual geometry rejection;
- solver/license failure.

## 4. Structured geometry diagnosis

Motor-CAD geometry exceptions are normalized into operator-level codes and canonical parameter hints. Current patterns cover Slot Opening and Stator/StatorAir intersection messages and produce operator actions. Full raw Motor-CAD text and traceback remain archived for engineering diagnosis.

## 5. Current-session observability

`StructuredLogStore` now assigns one `BOOT-*` ID per application process. Every central JSONL record includes `session_id`.

The log query/summary/diagnostics APIs can filter by current session. The GUI defaults to this filter while preserving an explicit switch for historical investigation. Diagnostic bundles also record the current session metadata.

## 6. Result comparison

`ResultViewerService.compare_cases()` accepts 2–8 Case IDs. It builds a union of canonical parameters and scalar results, uses the first Case as baseline and computes absolute and relative deltas.

This comparison sits inside the existing Result Viewer rather than creating another top-level analysis page.

## 7. Worker lifecycle hardening

A full-suite regression exposed accumulated `multiprocessing.Queue` semaphore objects after many short Cases. `SolverProcessRunner` now uses one one-way `multiprocessing.Pipe` carrying progress, logs and the terminal frame. Real Motor-CAD still runs in an isolated spawned process.

Mock is an internal workflow/self-test solver, so TaskManager now executes it directly inside the existing Case thread. This removes unnecessary process startup in development/CI while preserving parallel Case scheduling and all Task/Case/result/Data Factory behavior.

## 8. Task terminal contract

`TASK_FINISHED` event/log emission is completed before the database exposes a terminal Task status. Once `/api/tasks/{id}/summary` reports COMPLETED/FAILED/CANCELLED, final observability writes and Data Factory ingestion have already completed.

## 9. Installation UX

`GET /api/system/installations` now returns:

- selected executable;
- discovered installations;
- Studio target Motor-CAD version;
- selected-version match status.

The GUI warns immediately when the manually selected EXE does not match the configured version mapping.

## 10. Known limits

V0.15 does not replace Motor-CAD geometric validation, does not enumerate all Graph Viewer names, and does not claim new real-solver qualification in this Linux/container environment. Complete material synchronization, Lab maps, unstructured FEA field visualization and persistent Motor-CAD session pooling remain later production work.
