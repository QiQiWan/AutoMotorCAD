# V0.89-C — Editor / Navigation Transaction Hardening

Release target: **MotorCAD Studio 0.89.3 / Schema 45**

## 1. Objective

V0.89-C closes the browser-side transaction boundary around engineering edits and navigation. The release treats editor save, route change, modal close, duplicate clicks and retry-after-unknown-response as one recoverable interaction system.

The operating rule is:

`Prepare -> Resolve latest intent -> Commit navigation -> Dispose old editor`

If the route commit fails, the router restores the last stable route/UI state. A guard may save or confirm pending work during Prepare, but it may not unmount the current editor before navigation is committed.

## 2. Navigation transaction authority

`NavigationTransactionAuthorityV1` is loaded before application/editor/router modules and provides:

- ordered editor guards with explicit priority;
- `prepare()` for pending-change persistence/confirmation;
- last-intent-wins semantics while asynchronous guard I/O is running;
- `run()` with commit and rollback callbacks;
- `withActionLock()` single-flight protection for duplicate write actions;
- global unsafe-change inspection;
- browser `beforeunload` protection while local-only changes exist;
- committed/blocked/failed transaction events used for deterministic post-navigation cleanup.

Current guard order is:

1. Design editor — priority 100;
2. Analysis configuration — priority 90;
3. Project editor — priority 70.

## 3. Design editor transaction

Design Revision commit now carries a stable `commit_key` for the exact pending Draft intent. If MotorCAD Studio commits the Revision but the browser loses the response, retrying with the same key replays the exact immutable Revision instead of creating a second Revision.

The backend persists the key inside immutable `editor_transaction` evidence and resolves replay while holding the same database lock used by normal commit.

Design route leave is two-phase:

1. flush the current Draft and prepare leave;
2. only after `mcs:navigation-transaction-committed`, dispose the editor and abort editor-local requests.

A failed or superseded route therefore leaves the editor mounted and recoverable.

## 4. Project editor transaction

Project settings now track a canonical baseline and detect unsaved name/description changes. Leaving settings, opening another project surface or entering Trash invokes one shared decision dialog:

- **继续编辑** — block navigation and preserve values;
- **放弃修改** — discard local edits and continue;
- **保存并继续** — persist once, then continue only after success.

Project create, save, trash and restore actions use single-flight locks. Rapid double-clicks share one in-flight write instead of issuing duplicate state transitions.

The project-card **基本信息** action is routed through the transaction-aware router, closing a prior bypass that could replace an editor containing unsaved data.

## 5. Analysis configuration transaction

Analysis configuration treats the currently visible editor as a transaction surface. Pending values are flushed before operations that can destroy or re-render the editing context:

| Transition | V0.89-C behavior |
|---|---|
| analysis step change | save current dirty editor, then change step |
| operating/input domain switch | save current domain, then render target domain |
| Common / Advanced switch | save relevant dirty editor, then switch mode |
| input refresh | save current input values, then refresh from server |
| analysis refresh | flush current editor, then reload analysis state |
| route leave | flush current editor through navigation guard |
| browser unload | warn while local-only changes remain |

Execution submission now uses a stable `submission_key` derived from the frozen execution intent. The key remains stable across unknown transport failures and changes only after a known intent-changing event such as Analysis Revision, Execution Plan or submission-control change. This aligns the browser retry path with the backend idempotency contract.

## 6. Dialog and overlay lifecycle

`StudioDialog` now provides deterministic close semantics:

- a closing action can fire once only;
- controls are disabled immediately after action selection;
- keyed dialogs de-duplicate repeated opens;
- `transitionend` is supplemented by a 320 ms removal fallback;
- navigation commit closes active dialogs through one authority;
- focus returns to the opener after close;
- Escape closes the top dialog.

This prevents invisible modal remnants, repeated destructive actions and background overlays that capture input after the visible dialog has gone.

## 7. Transaction/recovery matrix

| Failure or interaction | Required result |
|---|---|
| repeated Save click | one in-flight write |
| repeated project delete/restore/create | one state transition per action key |
| Design commit succeeded, HTTP response lost | same `commit_key` returns same Revision |
| Analysis submission response unknown | unchanged execution intent reuses same `submission_key` |
| slow first navigation then fast second navigation | later operator intent wins |
| navigation guard blocks | current editor remains mounted |
| route apply fails | last stable route/UI restored |
| project settings dirty on leave | explicit continue/discard/save decision |
| analysis control re-render | dirty current domain is persisted first |
| browser refresh/close with local-only edits | native browser unload warning |
| modal transition event missing | DOM removal by bounded fallback |

## 8. Qualification scope

V0.89-C qualification covers browser transaction contracts, Design commit replay, Project unsaved-change behavior, analysis submission-key stability, dialog lifecycle, complete-shell navigation and regression against V0.89-A/B and V0.88-D.

Licensed Windows + Motor-CAD 2026R1 workstation qualification remains a separate `0.88-F` native production gate. V0.89-C does not promote local browser/API evidence into workstation-native evidence.
