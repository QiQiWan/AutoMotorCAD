# MotorCAD Studio V0.30.0 — 工程师认知收敛与单一操作状态

## 1. 本轮目标

V0.21–V0.29 已建立严格的 Design Revision、Scenario Revision、Run Configuration、Task、Case、Execution Lease、Worker、Session 与 Validation Evidence。问题在于部分内部对象逐渐进入默认界面，工程师需要先理解 Studio 架构才能完成一次 Motor-CAD 计算。

V0.30 的目标是把默认工程界面重新压缩到工程师真正关心的链路：

**设计电机 → 设置分析 → 计算模型 → 分析结果**

底层版本化和运行时证据仍完整保留，只进入“高级/技术详情”。

## 2. V0.29 的主要可理解性问题

1. `Design Revision / Run Configuration / Execution Lease / Worker / Session / Fingerprint` 等追溯对象在普通流程中出现过多。
2. 顶层导航属于功能分类，缺少持续显示的工程任务链。
3. 仿真配置仍保留五步 Wizard 作为主交互，熟练工程师需要反复跳步确认上下文。
4. `PASS / WARNING / FAIL / QUALIFICATION / NATIVE VALIDATION` 等来源不同的状态同时出现，用户很难回答“现在到底能不能算”。
5. 错误卡仍有明显的日志语言，技术代码常常先于工程含义出现。
6. 计算监控把 Worker、资源租约和 Execution Lease 暴露在主视图，遮蔽真正的计算阶段。
7. 结果查看器首先回答“有哪些模块和数据”，没有优先回答“这次设计结果是否值得继续”。
8. 运行环境首页包含 Worker Pool、资源调度、Contract 等内部能力，首次使用负担过大。

## 3. V0.30 信息架构

项目内维持五个目的地用于直接定位，但工程流程条固定表达四个工程任务：

1. **设计电机**：结构、几何、永磁体、绕组、材料。
2. **设置分析**：电机版本、运行工况、分析类型、计算方式、结果选择。
3. **计算模型**：Motor-CAD 检查、求解进度、有限元过程。
4. **分析结果**：关键性能、质量提示、曲线/FEA、设计比较。

“数据资产”属于结果之后的次级工程能力，不参与一次普通计算的主链路。

## 4. 单一用户状态模型

默认 UI 只消费五个状态：

- `READY` → 可以计算
- `NEEDS_CHECK` → 需要检查
- `BLOCKED` → 无法计算
- `RUNNING` → 计算中
- `COMPLETED` → 已完成

底层的 Runtime Gate、Geometry Guard、Winding Guard、Qualification、Execution Lease、Quality Status 继续存在，但由 UI Guidance 层转换为一个可操作结论。

新增：

- `config/ui_terms.yaml`
- `motorcad_studio/ui_guidance.py`
- `GET /api/ui/lexicon`
- `GET /api/projects/{project_id}/ui-guidance`

项目概览由 Guidance API 直接返回 `headline / reason / action / route`，减少前端各页面自行解释状态。

## 5. 工程词汇层

V0.30 统一默认工程词汇：

| 内部对象 | 默认 UI |
|---|---|
| Design | 电机方案 |
| Design Revision | 设计版本 |
| Scenario Revision | 运行工况 |
| Solver Profile | 计算设置 |
| Output Profile | 结果设置 |
| Run Configuration | 本次计算配置 |
| Task | 计算记录 |
| Case | 计算算例 |
| Execution Lease | 执行技术信息 |
| Worker | 计算进程 |
| Session | Motor-CAD 会话 |

内部 ID 与哈希继续出现在技术详情和诊断包中。

## 6. 设置分析页面收敛

Engineering 模式不再把五步 Wizard 作为强制分页。原有五个配置区在同一页面连续展示：

- 电机模型
- 运行工况
- 分析与计算方式
- 需要的结果
- 检查并开始计算

Guided 模式仍保留逐步向导。

以下字段移动到“高级计算设置”：

- Task 名称
- 模板内部来源
- Solver mode
- Quality Profile

分析类型移动到“分析与计算方式”，避免在“电机基线”中混入求解概念。

临时 Design override 明确改名为“临时修改电机参数（可选）”，并说明长期修改应回到“设计电机”创建新版本。

## 7. 动态主操作

右侧“本次计算”仅突出一个主动作：

- 尚未选择电机 → 选择电机
- 未检查 → 检查当前配置
- 有阻断 → 定位问题 / 修复运行环境
- 可以计算 → 开始计算
- 正在提交 → 查看状态

工程师无需在“快速检查 / 原生预检 / 提交任务 / 刷新 Gate”等多个按钮之间判断先后顺序。独立 Motor-CAD 预检仍保留为排障能力。

## 8. 错误提示格式

V0.30 用户错误卡统一为：

1. **发生了什么**
2. **为什么**
3. **影响**
4. **怎么处理**

技术代码进入折叠的“技术详情”。

例如 `MOTORCAD_WINDING_SLOT_FILL_OVER_ONE` 默认显示“绕组槽满率过高”，并解释真实槽形/导体、计算影响和推荐修改参数；原始 code 与 Motor-CAD 消息仍可展开查看。

## 9. 运行环境收敛

普通运行环境页面只强调：

- Motor-CAD.exe
- 基础/深度检查
- 是否可以继续项目计算

Worker Pool、许可证本地容量、内存调度和 Runtime Contract 被移动到“高级运行信息”折叠区。

## 10. 计算监控收敛

Engineering 模式优先显示：

- 当前计算阶段
- 进度
- Motor-CAD 求解过程/FEA 可视化
- 是否需要处理问题

Worker、Runtime Resource Lease、Execution Lease 默认隐藏到技术视角；Expert/Developer 仍可查看。

## 11. 结果首页

打开完成 Case 后，在完整 Result Viewer 之前新增“工程结果摘要”：

- 结果是否完整
- 当前是否存在质量提示
- 轴转矩、效率、输出功率、总损耗、绕组最高温度、磁钢损耗等可用关键指标
- 修改电机
- 与其他结果比较

质量提示统一使用与模型错误相同的工程解释卡。

## 12. 兼容性边界

V0.30 没有删除以下底层对象或 API：

- Design/Scenario/Solver/Output Revision
- Run Configuration
- Task/Case
- Resource Lease
- Execution Lease
- Worker/Session
- Validation Evidence
- Fingerprint/Registry hash

它们仍是可追溯计算和故障诊断的基础。V0.30 只改变默认呈现层。

5. Case 完成后工程结果摘要是否与原 Result Viewer 数据一致。
