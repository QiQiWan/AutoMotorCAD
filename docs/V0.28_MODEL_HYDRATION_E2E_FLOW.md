# MotorCAD Studio V0.28 — 模型首帧水合与端到端计算流程收敛

## 1. 本轮问题

V0.27 运行时资源调度已经能够把 Worker、Studio 本地许可证容量与内存准入统一成一个资源租约，但实际操作仍存在两个影响很大的断点：

1. 从 Design Revision 进入计算配置时，参数输入框被 Revision 覆盖后，快速几何首帧仍停留在模板默认参数；用户第一次修改任意字段后才触发重新绘制。
2. 日常提交 Task 仍要求后端先运行一次独立 Motor-CAD 深度 Preflight。正式 Task 随后又会在 Persistent Worker / Execution Lease 中重新加载模型、回读参数、执行原生几何/绕组校验再求解。两个不同 Motor-CAD 实例形成重复门禁，也给“预检实例失败、正式实例其实可运行”留下了流程阻断点。

V0.28 将这两条链统一到一个权威模型快照和一个权威执行路径。

## 2. 快速几何首帧根因与修复

旧流程：

```text
选择 Design Revision
  ↓
按 Template defaults 渲染参数控件和快速几何
  ↓
把 Revision.parameters 写回 input
  ↓
没有重新 renderLiveDesignPreview()
  ↓
首帧仍显示模板默认模型
  ↓
用户修改任一 input
  ↓
input listener 触发 renderLiveDesignPreview()
  ↓
这时才与当前参数一致
```

这与现场现象完全一致。

V0.28 将 `applyTaskDesignRevision()` 设为唯一的 Task Builder 水合入口：

```text
Template defaults
  ↓
Design Revision effective parameters
  ↓
Scenario / material context
  ↓
重建 Task baseline
  ↓
参数 Inspector
  ↓
快速几何首帧
  ↓
Task summary / readiness
```

`useWorkspaceRevisionAsTask()` 不再自行复制一套不完整的初始化逻辑，而是注册 Revision 后直接调用 `applyTaskDesignRevision()`。

### 2.1 Revision baseline 重基准

V0.28 还修复了一个容易混淆的细节：控件原来的 `data-default` 来自模板，而 Task Builder 的语义应该以当前 Design Revision 为基线。

现在 Revision 水合完成后，所有参数字段都会写入：

```text
data-default          = 当前 Revision 水合后的值
data-revision-baseline = 当前 Revision 水合后的值
```

因此：

- 首次进入 Revision 时不会把“Revision 与模板不同”误显示为“本次 Task 修改”；
- `changed` 样式代表真正的 Task override；
- 参数修改数与 `taskOverrideCount()` 的工程语义一致；
- 后端仍可根据 Design Revision 自身的 `explicit_parameter_ids` 追踪设计变更，不需要前端把 Revision 基线重复声明成 Task override。

### 2.2 Workbench 快照权威化

`GET /api/design-revisions/{revision_id}/workbench` 新增：

```json
{
  "effective_parameters": {},
  "preview_signature": "sha256...",
  "preview_source": "design_revision_effective_parameters"
}
```

其中 `effective_parameters = template defaults + immutable revision parameters`。

Workbench 前端首帧直接由该快照初始化，而不依赖“先画模板，再等待输入事件纠正”。Inspector 会显示当前预览参数源和快照签名。

## 3. 日常计算流程为什么仍可能跑不通

V0.27 以前，正常 Task 提交存在两套 Motor-CAD 原生检查：

```text
前端完整检查
  ↓
后端 /api/tasks
  ↓
独立 Motor-CAD deep preflight  ← 单独实例 A
  ↓ PASS
创建 Task
  ↓
Runtime Resource Lease
  ↓
Persistent Worker
  ↓
加载真实 Case                ← 实例 B
  ↓
参数回读
  ↓
Geometry / Winding Native Validation
  ↓
Full Solve
```

独立实例 A 与真正求解的实例 B 不共享模型状态。V0.26 已经建立同一 Worker / Session 的 Validate-and-Run Execution Lease，因此继续把实例 A 作为日常提交硬门禁会增加启动次数和失败面，也不能提高正式求解证据的权威性。

## 4. V0.28 新的单一路径

正常操作流程改为：

```text
Design Revision effective snapshot
  ↓
快速提交检查
  ├─ API / domain validation
  └─ Studio deterministic geometry/winding guard
  ↓
非启动式运行环境准入
  ├─ Python / PyMotorCAD 静态可用性
  └─ 有效 Motor-CAD.exe 路径
  ↓
Task 创建（幂等）
  ↓
Atomic Runtime Resource Lease
  ├─ Worker
  ├─ Studio declared license capacity
  └─ memory admission
  ↓
Execution Lease
  ↓
同一 Persistent Worker / Motor-CAD Session
  ├─ canonical model load
  ├─ parameter write/readback
  ├─ material application
  ├─ native Geometry validation
  ├─ native Winding validation
  └─ Validation Evidence Hash
  ↓
Full Solve
  ↓
Native FEA / outputs / result quality
```

### 4.1 深度 Preflight 的新定位

深度 Motor-CAD Preflight 保留在“运行环境”页面，用于安装、RPC、许可证和工作站诊断。

计算页面中的“Motor-CAD 独立预检”也保留为可选诊断动作，但不再属于普通 Task 提交硬门禁。

真正决定“这个 Case 是否具备求解条件”的原生证据来自 Task 自己的 Execution Lease。

## 5. 非启动式提交准入

新增：

```text
GET /api/runtime/submission-readiness
```

该接口不会启动 Motor-CAD，仅检查日常提交必须具备的静态条件：

- PyMotorCAD / Python automation 环境；
- 当前有效 Motor-CAD.exe（若显式绑定）；
- 若没有显式 EXE，则说明会依赖已注册 Automation 安装；
- 当前有效运行路径变更后立即刷新前端准入状态。

返回中显式声明：

```text
authority = submission_static_readiness
native_validation_authority = task_execution_lease
```

## 6. Persistent Worker 交通故障的一次性隔离回退

Persistent Worker 可以提高启动效率，也增加 IPC/Owner 生命周期这一层基础设施风险。V0.28 对非常窄的 Worker 交通故障增加一次隔离进程回退：

允许回退：

- Worker pipe/IPC 通信失败；
- Worker 进程异常退出；
- Worker 没有返回最终 result frame。

禁止回退：

- Geometry invalid；
- Winding invalid / Slot Fill；
- License unavailable；
- Motor-CAD/PyMotorCAD 能力握手不兼容；
- 参数映射或模型工程错误。

回退仍保留同一个 Runtime Resource Lease，并在隔离求解进程内部重新执行 Validate-and-Run。事件记录为：

```text
PERSISTENT_WORKER_FALLBACK_ISOLATED
```

这样可以提高基础设施容错，同时不会把真实工程失败“重试成成功”。

## 7. 新的操作员执行流可视化

“检查并提交”区域新增 6 段执行流：

```text
Design 快照
→ 快速提交检查
→ 运行环境
→ Task + 资源租约
→ Motor-CAD 原生校验
→ 求解与结果
```

每一步区分：已完成 / 当前 / 阻断 / 后续。

操作员可以直接看到当前卡在：

- Design 快照；
- Studio 快速检查；
- 运行环境静态准入；
- Task 调度；
- Motor-CAD 原生模型校验；
- Full Solve / Result extraction。

不再把“任务没跑起来”统一显示成一个模糊的“未通过”。

## 8. V0.27 运行时能力继续保留

V0.28 完整包含 V0.27 的运行时收敛：

- Worker + Studio 本地许可证容量 + 内存的原子资源租约；
- 有效 Motor-CAD.exe 路径单一权威；
- Persistent Worker capability handshake；
- Runtime Contract 证据；
- Worker generation、RSS、Case 数回收；
- Execution Lease / Validation Evidence；
- Windows endurance campaign 脚本。

## 9. 验收建议

### 9.1 快速几何

1. 打开一个与模板默认值不同的 Design Revision；
2. 不触摸任何输入框；
3. 检查参数输入、Inspector、快速几何、Revision baseline 是否首帧一致；
4. 切换另一 Revision；
5. 快速几何应立即更新，无需先修改参数；
6. 修改一个参数后，只有该 Task override 被标记为 changed；
7. 恢复 Design Revision 后 changed 数应回到 0。

### 9.2 计算主流程

1. 运行环境页绑定目标 Motor-CAD.exe；
2. 在计算页选择 Design Revision；
3. 点击“快速检查”或直接“检查并计算”；
4. 普通提交过程中不应先弹起一个独立 Motor-CAD 做深度 Preflight；
5. Task 创建后进入实时监控；
6. 查看 Runtime Resource Lease；
7. 查看 Execution Lease；
8. 确认 Native Geometry/Winding Validation 与 Full Solve 使用同一 Worker generation / Session；
9. 若 Persistent Worker IPC 故障，检查是否只出现一次 `PERSISTENT_WORKER_FALLBACK_ISOLATED`；
10. 若模型本身错误，应直接保留工程根因且不做基础设施回退。
