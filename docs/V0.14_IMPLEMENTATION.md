# MotorCAD Studio V0.14 Implementation

## Scope

V0.14 is a runtime-correctness and operator-integration release derived from a real V0.13 Windows diagnostic bundle. The release deliberately prioritizes parameter intent, geometry safety, executable selection, frontend/backend consistency and a single result workflow over new solver breadth.

## Explicit parameter intent

`TaskCreate.explicit_parameter_ids` records parameters intentionally edited by the operator. The server additionally derives intent from values changed from template defaults, Sweep parameters, CSV matrix keys and DOE/optimization variables. Motor-CAD receives only those canonical EMag parameters. Untouched MTT defaults remain catalog/reference values and are not forced into the loaded runtime template.

This addresses the real e14 failure where a template reached `check_if_geometry_is_valid()` with an invalid Slot Opening / StatorAir relationship after parameter application.

## Geometry recovery

`MotorCADSolverAdapter._validate_model()` now records the original Motor-CAD error, snapshots runtime parameters, invokes `check_if_geometry_is_valid(1)`, revalidates, then compares runtime values. If recovery changes a user-explicit design parameter, the case is blocked. If only dependent, non-explicit geometry is adjusted, the calculation may proceed with an audit warning. `model_validation.json` is written even for blocking recovery failures.

`slot_opening` is now a canonical engineering parameter mapped to `Slot_Opening` for the 2026R1 registry.

## Requested vs effective parameters

The solver now captures final runtime defaults after validation and records them as `effective_parameters`. Quality checks use effective values where available. Data Factory curated `param.*` columns use effective runtime values, while differing request intent is retained under `requested_param.*`. This prevents a dataset from claiming an MTT candidate value that was never actually written to or used by Motor-CAD.

## Deployment consistency

V0.14 exposes `/api/client-contract`, stamps the frontend with a matching version, appends `?v=0.14.0` to static assets, and sends no-cache/no-store headers for the application shell/static code. The UI explicitly warns when frontend and backend versions differ. This directly addresses the diagnostic bundle showing 404 responses for routes that exist in the V0.13 source package.

## Motor-CAD executable selection

When Registry/filesystem discovery is insufficient, the operator can paste an executable path or open a native Windows OpenFileDialog. The existing runtime selection file remains the single source used by subsequent Solver adapters.

## Result workflow

The standalone analytics navigation is removed. Existing task analytics are preserved inside the Result Viewer batch mode. Single-case viewing, raw artifacts, field results, DOE/Pareto, sensitivity and multi-case overlays now share one entry point.

## Monitoring correction

A Motor-CAD process with no active Studio worker is no longer automatically classified as an orphan. It is informational unless Studio can prove ownership; this avoids penalizing system health for a manually opened or still-exiting Motor-CAD instance.
