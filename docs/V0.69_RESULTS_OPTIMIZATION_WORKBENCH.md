# MotorCAD Studio V0.69.0 — Results & Optimization Workbench

## 1. 本轮目标

V0.69 沿既定路线完成“结果 → 比较 → 参数研究/优化 → 候选固化 → 新 Design Revision”的闭环，并继续使用 V0.67 的不可变 Design/Analysis/Run Configuration 血缘以及 V0.68 的 Motor-CAD Native Parity 资格状态作为结果可信边界。

当前交付环境为 Linux，无法运行许可化的 Windows Motor-CAD 2026R1，因此本轮完成的是 Studio 侧 Results & Optimization Workbench、计算合同、比较规则、优化工作流和资格边界接入。`native_motorcad_workstation_qualification_percent` 继续保持 0%，没有将 mock/单元测试结果记作 Motor-CAD 原生资格证据。

## 2. V0.69 最终工程链

```text
Design Revision
    ↓
Analysis Revision + 单一选定 Operating Point + Solver/Input/Output
    ↓
V0.67 Precheck + immutable Run Configuration
    ↓
Motor-CAD Task / Cases
    ↓
quality-aware Results
    ├─ 单 Case 原生结果/FEA
    ├─ 同一 Task 的 2–8 Case 工程比较
    ├─ 同一 Design 的 2–6 Revision 横向比较
    └─ 参数扫描 / DOE / Pareto / NSGA-II
            ↓
       feasible / Pareto / objective-best / balanced candidate
            ↓
       2–8 candidate Case comparison
            ↓
       promote design variables only
            ↓
       new immutable Design Revision
```

## 3. Results Workbench 收敛

结果页现在由稳定 `static/results/` 模块拥有，形成 5 个明确入口：

1. **结果总览**：项目结果健康度、最近 Task、可用 Case、优化任务和 Native Parity 状态。
2. **单 Case**：沿用现有质量感知 Result Viewer，查看标量、曲线、FEA 与归档证据。
3. **Case 比较**：同一 Task/Run Configuration 内的 2–8 Case 工程对照。
4. **版本比较**：同一 Motor Design 的 2–6 Design Revision 横向对照。
5. **参数研究与优化**：Sweep、Latin Hypercube、Pareto Search、NSGA-II 与候选固化。

稳定模块为：

- `static/results/workbench.js`
- `static/results/case-compare.js`
- `static/results/revision-compare.js`
- `static/results/optimization.js`

上述模块均由 Router 驱动，没有新增 `setTimeout()` 作为页面状态所有权机制。

## 4. 通用 Case 工程结果比较

V0.69 增加精确路由：

```text
/app/projects/{project}/results/case-compare/{task}/cases/{case1,case2,...}
```

比较规则在服务器端进一步收紧。新增：

```text
GET /api/tasks/{task_id}/result-comparison?case_ids=...
```

服务器要求：

- 2–8 个互不重复的 Case；
- 所有 Case 必须属于同一个 Task；
- Task 必须真实存在；
- Case 必须真实存在。

如果前端或外部调用尝试把其他 Task 的 Case 混入，返回结构化 `CASE_COMPARISON_TASK_MISMATCH`。因此通用比较不会把不同 Run Configuration、不同 Solver 或不同冻结输入下的结果直接呈现为一个干净的设计参数对照。

比较界面同时展示：

- Case 质量状态；
- execution status；
- Run Configuration / Design Revision 血缘；
- 标量结果及相对首个基准 Case 的绝对/百分比变化；
- 发生变化的设计参数；
- 工况变化；
- Solver 设置变化；
- Pareto/方向性辅助信息；
- 每个 Case 的单独结果入口。

第一项选中 Case 固定为基准，选中顺序具有明确语义。

## 5. Design Revision 横向比较

新增：

```text
GET /api/designs/{design_id}/revision-compare?revision_ids=R1,R2,...
```

限制在同一 Motor Design 的 2–6 个 Revision。

参数和材料差异总是可以对照；性能结果采用更严格规则。只有结果证据的 comparison signature 完全一致，才计算跨 Revision 的性能 delta。签名包含：

- Analysis 类型；
- Solver mode；
- quality profile；
- template；
- operating scenario；
- solver settings。

另外，本轮修复了一个容易造成错误工程结论的问题：DOE/优化 Case 会在 Case 层覆盖设计变量，但仍携带基准 `design_revision_id`。这些 Case 现在明确从“冻结 Design Revision 的性能证据”中排除，避免将优化候选误认为原始 Revision 的运行结果。

若结果证据不满足一致签名，界面仍显示对应证据和质量状态，但不计算伪性能比较。

## 6. 参数研究与优化合同

参数研究严格绑定：

- 一个 immutable Design Revision；
- 一个 immutable Analysis Revision；
- 一个显式选择的 operating point；
- 该 Analysis 的 input domains；
- solver settings；
- requested outputs。

V0.69 暂不把同一电机的多个 operating point 当作独立优化个体。每个优化任务只冻结一个 operating point，避免 NSGA-II/Pareto 搜索把“设计变化”和“工况变化”混为同一搜索维度。

支持 4 种工程策略：

- Full-factorial Sweep；
- Latin Hypercube DOE；
- Pareto Candidate Search；
- NSGA-II。

提交前服务器确定性估算 Case 规模，并设置 **5000 Case** 工程安全上限。超过上限直接拒绝，不进入 Motor-CAD 队列。

## 7. 设计变量与目标/约束

`GET /api/analysis-definitions/{analysis_id}/optimization-catalog` 从当前 Design Revision 和参数注册表生成数值设计变量目录，并给出当前值、合法上下限和建议 ±10% 搜索范围。

operating/environment/cooling/topology 类参数不会默认列为推荐连续优化变量；拓扑参数被显式选择时会产生工程警告。

多目标搜索支持 2–8 个唯一目标。V0.69 增加了重复 objective ID 的模型级拒绝，防止两个相同结果指标被伪装成“多目标”。

本轮进一步补齐结果可行性约束编辑器。用户可以直接配置：

```text
result.<output> <= threshold
result.<output> <  threshold
result.<output> >= threshold
result.<output> >  threshold
result.<output> == threshold
```

约束输出若原 Analysis 没有请求，会自动加入该优化 Task 的 immutable requested outputs，确保可行性判断拥有结果证据。

## 8. Preview / Submit / 并发安全

参数研究提交继续复用 V0.67 的工程执行边界：

- stale Analysis Revision guard；
- stale Design Revision guard；
- Studio precheck；
- runtime readiness；
- 可选/复用 Motor-CAD native precheck evidence；
- immutable Run Configuration；
- idempotent submission key。

新增普通工程接口：

```text
POST /api/analysis-definitions/{analysis_id}/experiments/preview
POST /api/analysis-definitions/{analysis_id}/experiments/execute
```

Preview 不启动真实求解，只生成权威 Case 预算和任务合同检查结果。Execute 会再次绑定当前 Revision identity；如果其他窗口已更新 Design 或 Analysis，会返回 stale conflict，避免在用户看着旧配置时静默提交最新版。

## 9. 优化结果工作台

新增：

```text
GET /api/tasks/{task_id}/optimization-workbench
```

输出包含：

- evaluated / feasible / infeasible 数量；
- Pareto front；
- 每个 objective 的最优候选；
- result constraints；
- generation convergence；
- candidate variables；
- candidate objective values；
- quality state；
- constraint violation；
- optimizer run state；
- Native Parity trust boundary。

对于前两个 objective，界面提供 Pareto 2D 分布。多于两个 objective 的完整候选仍保留在表格与优化摘要中。

“平衡候选”采用当前可行 Pareto 集上的 equal-weight normalized Euclidean distance。它仅作为快速决策辅助，没有被定义为工程最优解；正式方案仍需结合目标权重、约束裕量、质量状态、原生资格和适用工况判断。

## 10. Candidate → Design Revision

新增：

```text
POST /api/cases/{case_id}/promote-design-revision
```

固化候选时，只写回该 experiment 的 explicit design-variable IDs。

以下 Analysis-owned 值不会进入 Design intent：

- shaft speed；
- current；
- DC bus voltage；
- phase advance；
- ambient/cooling；
- 其他 operating point 输入。

新版本沿用既有 immutable Design Revision 机制。可选 Analysis rebind 仍带并发检查；如果 Analysis 已经被另一个会话改到其他 Design Revision，不会静默覆盖。

## 11. Native Parity 边界

V0.69 消费 V0.68 的 version-scoped native parity matrix。

当前 Linux 交付环境没有执行许可化 Motor-CAD 2026R1 Windows qualification，因此：

```text
studio_implementation_completion_percent = 100
native_motorcad_workstation_qualification_percent = 0
```

这并不阻止用户进行探索性参数扫描和流程验证，但结果工作台会持续显示 qualification pending。用于正式工程决策时，应先在目标 Windows 工作站运行 V0.68 的 BPM/SPM/IPM/AFPM Native Parity suite，并确认当前模板对应 profile 已通过。

## 12. 本轮发现并修复的额外问题

### 12.1 结果比较作用域

仅依赖通用 `case_ids` 比较接口允许外部调用混入不同 Task 的 Case。V0.69 新增 same-Task authoritative endpoint，UI 和服务端同时限制作用域。

### 12.2 优化约束 UI 缺失

后端早已支持 experiment constraints，但原 V0.69 初版前端固定提交 `constraints: []`。当前已补齐约束编辑器和 requested-output 自动扩展。

### 12.3 重复多目标

两个相同 `result_id` 原先可以通过“至少两个 objective”的长度检查。当前模型级校验要求 objective ID 唯一。

### 12.4 720 px 动态约束行水平溢出

Playwright 在动态添加约束后捕获到 number input 的 min-content 宽度把工作台根节点撑宽 9 px。当前通过 grid item/input 的 `min-width: 0` 和 `width: 100%` 约束修复。此问题说明 V0.69 的布局测试不仅验证静态初始画面，也覆盖交互后动态 DOM。

## 15. Windows + Motor-CAD 2026R1 最终验收

在目标工作站上建议按下列顺序执行：

1. 先运行 `run_v068_native_parity_windows.bat`，确认待优化模板对应 BPM/SPM/IPM/AFPM profile PASS。
2. 在 Studio 创建一个基准 Analysis Revision，并以真实 Motor-CAD 求解获得基准 Case。
3. 在“结果 → 参数研究与优化”选择该 Analysis，先执行 1D Sweep，确认参数写入、Case 数和返回结果与 Motor-CAD 原生模型一致。
4. 执行 2–3 变量 Latin Hypercube，检查 Case fingerprint、Run Configuration 和 result quality。
5. 配置两个 objective 和至少一个 result constraint，执行 Pareto/NSGA-II。
6. 检查 Pareto 候选、objective-best、constraint feasibility、generation convergence 与 Motor-CAD 原始 CSV/变量结果的一致性。
7. 使用“Case 比较”对 2–8 个同 Task 候选做工程对照。
8. 将一个候选保存为新 Design Revision，确认只有 experiment design variables 发生变化。
9. 用同一个 Analysis 条件对新 Revision 重新计算，再进入 Design Revision 比较；确认 comparison signature 相同时才出现性能 delta。
10. 验证浏览器刷新、前进/后退后 Case/Revision/Optimization deep link 精确恢复。

## 16. V0.69 完成判定

Studio 侧 V0.69 功能范围已经闭环：

```text
quality-aware Results
→ same-Task Case compare
→ Design Revision compare
→ Analysis-pinned parameter study
→ constraints + Pareto / NSGA-II
→ candidate comparison
→ candidate promotion
→ new immutable Design Revision
```

剩余风险集中在目标 Windows Motor-CAD 2026R1 原生执行资格及真实优化任务的运行时/许可证/长时间求解表现。该部分必须使用 V0.68/V0.69 工作站证据关闭，不能由 Linux mock 回归替代。
