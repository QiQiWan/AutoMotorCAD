# V0.89-G2.3 Runtime Log Root-Cause Report

Date: 2026-08-28
Input evidence: supplementary runtime and calculation log package from the Windows Motor-CAD 2026R1 workstation.
Target baseline: MotorCAD Studio 0.89.9 V0.89-G2.2.
Patched target: MotorCAD Studio 0.89.9 V0.89-G2.3.

## Executive conclusion

The new evidence separates four different behaviors that had previously looked like one generic "Motor-CAD calculation failed" condition.

1. The native Motor-CAD model/runtime validation passed. The single-flight/cache repair from G2.1/G2.2 is working.
2. The EMag solver completed successfully. Its Case was later marked INVALID by a Studio-side native FEA normalization defect.
3. The steady thermal Case genuinely failed before solve because Studio synthesized an invalid raw automation variable named `LossSource`.
4. Runtime queueing was expected for a single persistent Motor-CAD worker, but the monitor incorrectly emitted stale-worker alerts while queued Cases did not own a worker yet.
5. Native screen capture was enabled by default and added an avoidable post-processing delay before failing on a headless/hidden Motor-CAD GUI path.

The package also contains one Lab magnetic Case with solver completion plus quality INVALID. The package does not contain enough Lab result-quality evidence to prove the exact quality defect. G2.3 therefore adds quality flags and first warnings directly to future `CASE_COMPLETED` log events instead of guessing the cause.

## Evidence summary

Session `BOOT-941CBA938B07` contains 118 exported events: 103 INFO, 10 WARNING and 5 ERROR. The exported health score was 40, but part of that degradation came from false queued-worker heartbeat alerts.

The standard validation campaign created four single-Case tasks in about four seconds:

| Task | Analysis | Final execution | Quality / failure |
| --- | --- | --- | --- |
| `TASK-CBD32DF5FC` | EMag | COMPLETED | INVALID |
| `TASK-6D42517FA3` | Lab magnetic | COMPLETED | INVALID |
| `TASK-9C44E5BC69` | Thermal steady | FAILED | raw automation write failure |

The runtime scheduler correctly reported worker capacity 1. Four runtime leases were granted with average wait 54.746 s and p95 wait 92.907 s. This is serial resource scheduling, not evidence that the Motor-CAD process itself was hung.

## Root cause A - EMag native FEA evidence false invalidation

### What actually happened

For `TASK-EBE7BC1082-C0001`, the persistent Motor-CAD worker completed successfully and the task finished as COMPLETED. The result bundle contains valid scalar/curve outputs, including shaft torque 3.63187465 Nm, a 61-point torque-angle curve and torque harmonics.

The Case quality was changed to INVALID only because `REQUIRED_FEA_EVIDENCE_INCOMPLETE` was raised. The old normalization result reported:

- `reason = no_numeric_points`
- missing required field `b`
- no visualization coordinates
- no replayable FEA frame

This diagnosis was false. Motor-CAD had produced native FEA data.

### Exact parser mismatch

Studio requested:

`RegCode,X,Y,B,Pt,J,JEddy`

The actual Motor-CAD ElementsTable in the supplied native sample is:

`TriIndex,Node1,Node2,Node3,RegCode,X,Y,B,Pt,J`

Motor-CAD omitted `JEddy` for this solution. G2.2 assumed each element row must contain:

`4 connectivity columns + len(requested_outputs)`

That assumption required 11 columns. The actual table had 10 columns, so every otherwise valid row was discarded before X/Y/B extraction. This produced the misleading `no_numeric_points` condition.

### G2.3 repair

`native_fea_stream.py` now treats the written native ElementsTable header as the column-layout authority. Requested outputs remain provenance only. Unsupported/omitted optional requested outputs are recorded under `missing_requested_outputs` and no longer shift all subsequent columns.

The supplied native sample was replayed through the patched parser:

- `normalized = true`
- source points: 5292
- frame count: 1
- available fields: `b`, `pt`, `current_density`
- requested outputs: `RegCode,X,Y,B,Pt,J,JEddy`
- exported outputs: `RegCode,X,Y,B,Pt,J`
- missing optional output: `JEddy`
- B range: 0.0 to 2.03 T
- current-density range: -5.37 to 5.37 A/mm2
- frame file SHA-256 and byte size are registered

`fea_evidence.py` now reports omitted requested outputs separately and blocks qualification only when a field required by the explicit FEA contract is actually missing.

## Root cause B - invalid Thermal `LossSource` automation variable

The thermal Case contains direct workstation evidence:

`[Therm] expert parameter write failed: LossSource: ... Could not find LossSource`

The execution plan also shows `motorcad_controls = ["Therm.LossSource"]` before the failure.

The source was Studio's input-domain materialization layer. A Studio semantic setting named `loss_source` was automatically translated into a guessed raw Motor-CAD variable `Therm.LossSource`. The supplied Motor-CAD 2026R1 workstation proves that this raw name is not valid for the current native model/context.

### G2.3 repair

- `loss_source` remains a Studio-level immutable physical-input semantic.
- Studio no longer synthesizes a raw `Therm.LossSource` variable.
- The unqualified built-in `LossSource` entry was removed from `solver_controls.yaml`.
- Existing saved Analysis Revisions carrying the old synthetic `automation.Therm.LossSource` or direct `Therm.LossSource` value are migrated at materialization time by retiring that control.
- Explicit expert `automation_overrides` remain separate and are not silently rewritten.

This preserves the design intent while requiring future native raw controls to come from a qualified Motor-CAD Automation Parameter Names registry.

## Root cause C - queue wait misclassified as stale worker

The campaign intentionally entered the single-worker queue. For the last EMag Case, runtime resource acquisition occurred after 92.907 s. The queue monitor correctly reported `RUNTIME_RESOURCE_QUEUE`.

However, the monitoring layer also emitted `WORKER_HEARTBEAT_STALE` after only 8-10 seconds for Cases still waiting for a runtime lease and without an owned worker PID. Those alerts later resolved with messages claiming heartbeats had been stale for 38.3 s, 84.4 s and 91.3 s. No worker existed for those queued Cases during most of that interval.

### G2.3 repair

Heartbeat staleness is evaluated only after a Case owns a concrete worker PID and the process identity is known. Queue wait remains represented by `RUNTIME_RESOURCE_QUEUE`. This prevents expected serialization from degrading system health as a false worker failure.

## Root cause D - default native screenshot path adds avoidable latency

For the supplied EMag Case, native FEA export/normalization activity reached the post-processing phase around 08:35:05-08:35:07 UTC. The screenshot attempt failed at 08:35:20 with:

`save_motorcad_screen_to_file ... failure`

The result bundle records that Motor-CAD did not create a screen image file. The numerical native FEA export is the authoritative result visualization source for this workflow; screenshot capture is auxiliary evidence.

### G2.3 repair

Native Motor-CAD screenshot capture is now opt-in for newly created Analysis definitions/recipes. Existing Analysis Revisions that explicitly enabled it remain unchanged. This removes the default GUI-dependent post-processing delay while retaining an explicit troubleshooting/qualification option.

## Previously observed items in this log package

The task payload still contains Design-vs-Analysis material differences such as `Copper (Annealed) -> Copper (Pure)` and `Aluminium (Alloy 195 Cast) -> Aluminium (Cast)`. This evidence comes from the pre-G2.2 saved Analysis semantics present when this run was generated. G2.2 already changed component-material ownership so Design Revision is authoritative and Analysis no longer redefines these component materials. G2.3 keeps that repair.

The session also contains an old frontend context rejection (`analysis must bind a verified motor revision`). G2.2 already hardened route reconciliation so a stale descendant route hint cannot bind an Analysis without its validated ancestor context. It is retained here as historical evidence, not treated as a new G2.3 root cause.

`Coil index too high` appears in native messages during winding probing. The same validation run reports winding, geometry and parameter roundtrip PASS, so the supplied evidence does not support promoting this message to the current blocking root cause.

## Remaining unresolved item - Lab magnetic quality INVALID

`TASK-6D42517FA3` completed its solver path and was marked quality INVALID. The supplied export does not contain its full Case diagnostics/result quality flags, so assigning a cause would be speculative.

G2.3 adds the following payload to future `CASE_COMPLETED` events:

- `quality_status`
- `result_bundle_id`
- first result warnings
- result quality flags

A new G2.3 workstation run should therefore make the Lab invalidation diagnosable from the normal runtime log package even when that Case's full diagnostics directory is not exported.

## Code changes

- `motorcad_studio/native_fea_stream.py`: parse actual native table headers; retain requested/exported/missing output provenance.
- `motorcad_studio/fea_evidence.py`: distinguish omitted optional requested fields from required FEA-contract failures.
- `motorcad_studio/engineering_precheck.py`: stop synthesizing `Therm.LossSource`; retire the legacy saved synthetic control.
- `motorcad_studio/config/solver_controls.yaml`: remove the unqualified `LossSource` built-in control.
- `motorcad_studio/monitoring.py`: do not run worker-heartbeat checks before worker ownership exists.
- `motorcad_studio/solvers/motorcad.py`, `analysis_guidance.py`, `analysis_recipes.yaml`, `unified-configuration.js`: native screenshot capture becomes opt-in by default.
- `motorcad_studio/static/analysis/standard-validation.js`: explicitly explain serial queueing by worker/license capacity after campaign submission.
- `motorcad_studio/task_manager.py`: include Case quality flags/warnings/result-bundle identity in future completion logs.
- `tests/test_v089g23_log_root_cause_repairs.py`: regression coverage for the above root causes.

## Required Windows acceptance run

Run the Standard Validation package again on the same project with G2.3 and verify all of the following:

1. EMag native FEA evidence reports a populated B field and replayable frame; `REQUIRED_FEA_EVIDENCE_INCOMPLETE` must not appear when B/X/Y exist.
2. Thermal execution must not issue `set_variable("LossSource", ...)` and must proceed beyond input application.
3. Cases waiting for the single Motor-CAD worker may raise `RUNTIME_RESOURCE_QUEUE`, but must not raise `WORKER_HEARTBEAT_STALE` before a worker PID is assigned.
4. New Analysis definitions should have native screenshot capture disabled by default. Enable it only when a GUI screenshot is explicitly required.
5. If the Lab magnetic Case remains INVALID, export the new G2.3 logs. Its `CASE_COMPLETED` payload should now contain the exact quality flags/warnings needed for the next root-cause pass.
6. Confirm G2.2 material ownership remains effective: component materials originate from the Design Revision and are not re-entered by Analysis configuration.

## Release boundary

G2.3 repairs deterministic defects demonstrated by the supplied workstation evidence. It does not claim formal Windows production qualification until the patched package is rerun on the licensed Motor-CAD 2026R1 workstation and the acceptance items above are satisfied.
